1. Назначение

Провайдер переводит вызовы файлового API VS Code по URI объекта архива в чтение этого объекта из
ZIP-архива: stat — сведения о файле, readFile — его содержимое, watch — слежение за архивом.
Других задач у него нет.

Кто вызывает. Только VS Code: для вкладок (открытие, восстановление, обновление), workspace.fs и
наблюдателей. Через VS Code приходят редактор архива (vscode.open по построенному им URI), другие
расширения и сам провайдер, когда архив — запись другого архива (URI Т5). Кто стоит за вызовом,
провайдер не знает; с редактором архива его связывает только формат URI.

Не решает:
- изменение архива — файловая система только для чтения;
- каталоги файловой системы: иерархию, readDirectory, архив как папку рабочей области [Р1,
  URI Р12];
- содержимое файлов записи-каталога и корня — его задаёт расширение (3.10) [Р16];
- список записей, читаемые имена, даты и прочие сведения о записях — это редактор архива;
- распаковку на диск, пароли, восстановление повреждённых архивов [Р15];
- отождествление одного архива под разными URI [URI Р4].

Цели (Ц1–Ц8). Правила — в разделе 3, как цели достигнуты и где их пределы — в разделе 4.

Ц1. Верность: readFile записи-файла отдаёт данные именно той записи, которую называет URI,
    распакованные и сверенные с центральным каталогом, — или отказывает. Ни чужих, ни неполных, ни
    несверенных байтов.
Ц2. Только чтение: провайдер ничего не пишет — ни в архив, ни на диск, ни во временные файлы.
Ц3. Обновление: открытая вкладка следует за архивом — запись изменилась, пропала, появилась.
Ц4. Недоверенный архив: архив — чужие данные. Память и работа ограничены заявленными размерами и
    пределами; вне архива ничего не читается, ничего не исполняется.
Ц5. Не мешать: между вызовами архив не открыт — его можно удалить, заменить, перезаписать;
    память держится, пока за файлами архива наблюдают.
Ц6. Любой архив: любой схемы, которую VS Code умеет читать, в том числе вложенный.
Ц7. Понятный отказ: «записи нет» отличимо от «запись есть, но не прочитать»; причина названа.
Ц8. По правилам VS Code: FileStat, события и отказы — такие, каких ждёт API FileSystemProvider.

Термины формата — как в URI 1: центральный каталог, запись, имя, index, запись-каталог (имя на
"/", [URI Р12]), запись-файл (любая другая), корень, объект, архив, провайдер, генератор.

Слоёв два, и слова у них разные:
- файловая система "zip-document" — то, что видит VS Code. В ней файл — ресурс с типом
  FileType.File, каталог — ресурс с типом FileType.Directory. Слово «каталог» без «центральный»
  в этом документе значит только это;
- архив — то, что лежит в ресурсе архива: центральный каталог и его записи, записи-файлы и
  записи-каталоги.
Как объекты архива становятся файлами — раздел 2.

Кроме того:
- URI объекта — канонический URI (URI 3.4): URI записи или URI корня; P — URI архива из него;
  тройка — (архив, имя, index) URI записи (URI 3.5);
- ресурс архива — то, что называет P, в его файловой системе;
- версия архива — содержимое ресурса архива в некоторый момент;
- заявленное — сведения записи центрального каталога: флаги, метод, размеры, CRC-32, смещение;
- данные записи — её распакованные байты;
- содержимое файла — то, что отдаёт readFile;
- расширение — документ реализации, задающий содержимое файлов записи-каталога и корня (3.10);
- архив на диске — P схемы "file": провайдер читает его с диска хоста, где работает сам; архив не
  на диске — любой другой схемы, в том числе "zip-document";
- наблюдение — вызов watch, чей Disposable ещё не освобождён;
- отказ — FileSystemError, которым завершился вызов;
- пределы — настройки 3.9.


2. Модель

Каждый URI объекта — файл файловой системы "zip-document"; других ресурсов в ней нет. Каталогов
в ней нет: ни один объект архива не становится каталогом [Р1].

  объект архива         файл          содержимое и размер
  запись-файл           URI записи    данные записи, заявленный исходный размер
  запись-каталог        URI записи    по расширению (3.10)
  центральный каталог   URI корня     по расширению (3.10)

Этот документ задаёт содержимое только в первой строке: запись-файл отдаётся как есть, один к
одному. Для файлов записи-каталога и корня он задаёт всё, кроме содержимого и размера [Р16].

Файл существует в версии архива, если ресурс архива есть и читается как ZIP, и:
- URI записи — в центральном каталоге не меньше index + 1 записей с этим именем; файл — запись
  номер index среди них в порядке центрального каталога;
- URI корня — всегда.
Время файла — время ресурса архива [Р3].

Каждый вызов отвечает по одной версии архива (3.2).


3. Контракт

Вызовы:

  stat             FileStat файла                               3.3
  readFile         содержимое файла                             3.4, 3.10
  readDirectory    всегда отказ                                 3.5
  watch            наблюдение за файлом                         3.6
  onDidChangeFile  Created, Changed, Deleted наблюдаемых URI    3.6
  writeFile, createDirectory, delete, rename  отказ NoPermissions  3.7
  copy             не реализуется                               3.7


3.1 Регистрация

- Схема "zip-document", isCaseSensitive: true [URI Р11], isReadonly: true. Регистрирует её только
  это расширение и только один раз [URI Р10].
- Активация — onFileSystem:zip-document: вкладки с URI объектов VS Code восстанавливает после
  перезагрузки окна, и к этому моменту схема должна быть зарегистрирована.
- extensionKind "workspace": провайдер работает там же, где лежат архивы на диске, в том числе на
  удалённом хосте Remote [Р12].
- Работает в недоверенной рабочей области: capabilities.untrustedWorkspaces.supported: true [Р14].


3.2 Общее для всех вызовов

Проверка URI. Первым делом, до любого чтения, провайдер решает, каноничен ли URI (URI 3.4).
Неканонический URI: stat, readFile, readDirectory — отказ FileNotFound; watch — 3.6; операции
записи — 3.7. Архив при этом не читается [URI Р11, Р2].

FileNotFound — ровно в трёх случаях:
- URI не каноничен;
- ресурса архива нет: его файловая система ответила FileNotFound;
- URI записи, архив прочитан как ZIP, и записей с этим именем в нём не больше index.
Любой другой отказ — не FileNotFound: ресурс архива не читается как ZIP или повреждён, его файловая
система ответила другой ошибкой, запись есть, но провайдер её не отдаёт (3.4) [Р2].

Одна версия. Ответ на вызов строится по одной версии архива: найденный объект и содержимое файла —
из одного центрального каталога и одних байтов архива. Данные, не сошедшиеся с заявленным, — отказ
(3.4), а не смесь версий.

Свежесть. Вызов отвечает по версии, которая на месте в момент вызова, — с наблюдением и без. Новую
версию провайдер узнаёт по mtime и size ресурса архива: изменение, после которого они те же, он
может не заметить [Р8].

Одновременные вызовы допустимы в любом числе и порядке; ответ каждого зависит только от версии,
по которой он построен.

Сообщение отказа называет объект — его метку (URI 3.2) — и причину; при пределе — заявленный
размер, предел и имя настройки. Программы на текст сообщения не опираются.


3.3 stat

Файл существует → FileStat:
  type         FileType.File — у любого файла: записи-файла, записи-каталога, корня;
               символьная ссылка — запись-файл [Р1, Р13];
  size         у записи-файла — заявленный исходный размер (с учётом ZIP64); у записи-каталога
               и корня — длина содержимого по расширению (3.10);
  mtime        mtime ресурса архива в этой версии [Р3];
  ctime        ctime ресурса архива в этой версии;
  permissions  не задаётся: FilePermission.Readonly VS Code ставит сам по isReadonly.
У записи-файла stat не читает данных и не решает, отдаст ли их readFile: зашифрованная запись,
запись с неподдерживаемым методом, запись сверх предела существуют — отказывает только readFile
[Р5].
Иначе — отказ по 3.2.


3.4 readFile

Файл записи-файла существует → данные записи: ровно заявленный исходный размер байтов, CRC-32
которых равен заявленному. Файл записи-каталога или корня существует → содержимое по расширению
(3.10); отказы 1–6 ниже — только для записи-файла.

Отказ до чтения данных, если:
1. запись зашифрована — бит 0 флагов;
2. метод сжатия не поддерживается. Поддерживаются как минимум 0 (stored) и 8 (deflate); отказ
   называет номер метода. Набор может расти без новой редакции;
3. заявленный исходный размер больше zipDocument.maxEntrySize (3.9).
Отказ при чтении, если:
4. по заявленному смещению нет локального заголовка (байты 50 4B 03 04) или данные выходят за
   конец архива;
5. распаковка даёт больше заявленного размера — тогда она обрывается, не выйдя за него, — или
   меньше;
6. CRC-32 данных не равен заявленному.

Флаги, метод, размеры и CRC-32 берутся из центрального каталога; из локального заголовка — только
длины имени и extra-поля, чтобы найти начало данных. Остальные поля локального заголовка провайдер
не сверяет с центральным каталогом и ими не руководствуется [Р4]. Прочитанное, но не сверенное не
отдаётся ни целиком, ни частично.
Иначе — отказ по 3.2.


3.5 readDirectory

Любой существующий файл, в том числе записи-каталога и корня, — отказ FileNotADirectory;
несуществующий — отказ по 3.2. Списков провайдер не отдаёт [Р1].


3.6 watch и onDidChangeFile

watch(uri, options):
- неканонический URI — Disposable, который ничего не наблюдает: архив не читается, событий по
  этому URI не будет, исключения нет [Р2];
- URI объекта — наблюдение до освобождения Disposable. options (recursive, excludes) не влияют:
  наблюдается файл. Пока есть хотя бы одно наблюдение за каким-либо URI архива, провайдер следит
  за ресурсом архива; для вложенного архива — снова через VS Code и себя;
- при watch провайдер узнаёт, есть ли файл в текущей версии (2); если архив не прочитать —
  считает, что нет.

Новая версия. Провайдер узнаёт о ней из наблюдения за ресурсом архива или при вызове (3.2):
- ресурс изменился и читается как ZIP — новая версия;
- ресурса нет (FileNotFound) — новая версия, в которой нет ни одного файла;
- ресурс есть, но как ZIP не читается или прочитать его не удалось — не версия: событий нет,
  последней известной остаётся прежняя [Р10]. Вызовы в это время отказывают по 3.2.
Несколько изменений архива могут дать одну новую версию. Срок, за который провайдер узнаёт об
изменении, не обещан.

События. Узнав новую версию, провайдер для каждого наблюдаемого URI этого архива отправляет ровно
одно событие, все вместе — одним вызовом onDidChangeFile [Р9]:
  было нет, стало есть    Created
  было есть, стало есть   Changed — даже если содержимое то же
  было есть, стало нет    Deleted
  было нет, стало нет     события нет
Событие отправляется после того, как новая версия стала той, по которой отвечают вызовы: stat и
readFile, вызванные по событию, отвечают по ней. URI события — наблюдаемый URI, как есть.

Событий нет по URI без наблюдения и по неканоническим URI.


3.7 Операции записи

writeFile, createDirectory, delete, rename — отказ NoPermissions для любого URI, ничего не читая.
copy не реализуется: VS Code вызывает его, только когда источник и цель в одной файловой системе,
а копирование в "zip-document" — та же запись. Копирование из "zip-document" в другую схему
VS Code делает через readFile.


3.8 Ресурсы

- Между вызовами ресурс архива не открыт: ни дескриптора файла, ни незавершённого чтения [Р6].
- Архив на диске целиком не читается: при чтении центрального каталога — конец файла (EOCD,
  записи ZIP64) и сам центральный каталог; при readFile записи-файла — локальный заголовок и
  сжатые данные этой записи [Р12].
- Архив не на диске читается целиком через workspace.fs — другого чтения API VS Code не даёт.
  Размер сверяется с zipDocument.maxInMemoryArchiveSize по stat до чтения.
- Память между вызовами: пока за каким-либо URI архива есть наблюдение — разобранный центральный
  каталог, а у архива не на диске — и байты архива; без наблюдения — не дольше нескольких секунд
  после последнего вызова по этому архиву [Р7].
- Память на readFile записи-файла — заявленный исходный размер записи и буферы чтения
  постоянного размера, у архива не на диске — сверх байтов архива.
- Читается только ресурс архива. Вложенный архив провайдер сам не раскрывает: он читается, только
  когда пришёл вызов по URI, в P которого он назван [Р13].


3.9 Пределы

  zipDocument.maxEntrySize            по умолчанию 52428800 (50 МиБ)
      наибольший заявленный исходный размер записи-файла, данные которой отдаёт readFile.
  zipDocument.maxInMemoryArchiveSize  по умолчанию 209715200 (200 МиБ)
      сколько байтов архива провайдер держит в памяти: архив не на диске — целиком, архив на
      диске — его центральный каталог. Больше — архив не читается: отказ, не FileNotFound.

Пределы жёсткие: сверх них — отказ, без вопросов пользователю. Задаются только в настройках
пользователя, не рабочей области (scope "machine") [Р11]. Изменение действует на следующие вызовы,
без перезагрузки. Вложенный архив — данные записи внешнего, поэтому подчиняется обоим пределам.


3.10 Расширение

Содержимое и размер файлов записи-каталога и корня задаёт расширение — документ, который
реализация называет (имя и редакция) и прилагает к себе. Реализация без расширения этому
документу не соответствует [Р16].

Расширение задаёт для этих файлов: что отдаёт readFile, чему равен size, когда readFile
отказывает и какие у него пределы. Остальное для них задано здесь, и расширение этого не
меняет: регистрация (3.1); проверка URI, FileNotFound, одна версия, свежесть, сообщения (3.2);
type, mtime и ctime (3.3); readDirectory (3.5); watch и события (3.6); операции записи (3.7);
ресурсы, кроме памяти на readFile (3.8). size равен длине содержимого той же версии.

К расширению требования те же, что к этому документу: цели, контракт, гарантии и пределы,
обоснования, проверка, отклонённое; цели Ц2–Ц8 обязательны и для него.


4. Гарантии и пределы

Ц1, верность. Запись находится по байтам имени и номеру среди одноимённых — именно та, что называет
URI (URI Т2). Данные записи-файла сверены с заявленным по размеру и CRC-32 (3.4), и ни неполных,
ни несверенных данных readFile не отдаёт. Что верно для записи-каталога и корня, говорит
расширение (3.10). Пределы:
- верность — относительно заявленного: провайдер отдаёт то, что архив называет данными этой
  записи, а не «правильные» данные. Кто пишет архив, пишет и CRC-32;
- CRC-32 — не криптографическая проверка: случайная порча и смесь версий (архив перезаписан на
  месте во время чтения) проходят её с вероятностью около 2^−32;
- читается ли архив необычного строения (данные перед архивом, сигнатура EOCD в комментарии,
  неверные счётчики записей) — решает читатель ZIP, и разные реализации и версии могут решать
  по-разному. Обещано одно: если данные отданы, они сверены.

Ц2, только чтение. Операции записи отказывают (3.7), записывающего кода в провайдере нет;
временных файлов нет (3.8).

Ц3, обновление. Наблюдение живёт, пока открыта вкладка: VS Code вызывает watch один раз на URI,
сколько бы редакторов его ни показывали, и освобождает после закрытия последнего (6.1). Событие по
новой версии (3.6) и mtime, растущий вместе с mtime архива (3.3), — то, по чему VS Code
перечитывает открытый редактор (Ц8). Пределы:
- события зависят от наблюдения за ресурсом архива в его файловой системе: если она изменений не
  сообщает, событий нет до первого вызова, который обнаружит новую версию (3.2), — например,
  повторного открытия;
- срок события не обещан; изменения подряд могут слиться в одно;
- при любом изменении архива Changed получают все его наблюдаемые файлы, и VS Code перечитывает
  все открытые из него вкладки;
- архив, который перестал читаться как ZIP и не стал снова, оставляет вкладки с последними
  прочитанными данными, а новые вызовы отказывают с причиной [Р10];
- изменение, после которого у архива те же mtime и size (грубое время файловой системы, два
  изменения за один её шаг), может остаться незамеченным — так же, как у самого архива в VS Code;
- архив переименован или перемещён — для его URI это удаление: Deleted, вкладки за архивом не
  следуют (URI записи содержит URI архива);
- документ, открытый openTextDocument без редактора, наблюдения не получает (6.1) и сам не
  обновляется.

Ц4, недоверенный архив.
- Зип-бомба: заявленный размер сверяется с пределом до распаковки, распаковка обрывается на
  заявленном (3.4, шаги 3 и 5); степень сжатия значения не имеет. Записи с общими сжатыми данными
  (перекрывающиеся) читаются каждая отдельно, каждая — в своём пределе.
- Вне архива ничего не читается: имена не разрешаются как пути, символьные ссылки не разрешаются,
  вложенные архивы сами не раскрываются (3.8) [Р13].
- Ничего не исполняется и не пишется (Ц2), поэтому провайдер работает и в недоверенной рабочей
  области [Р14].
- Пределы: начатую распаковку не прервать — у API FileSystemProvider нет отмены, и запись в
  пределе распаковывается до конца; время разбора центрального каталога растёт с числом записей
  и ограничено только пределом на его размер.

Ц5, не мешать. Между вызовами архив не открыт (3.8): удалить, заменить, перезаписать его
провайдер не мешает ни на какой системе, в том числе пока из него открыты вкладки; мешать может
только идущий вызов. Память — 3.8. Пределы:
- у вложенного архива каждый уровень, кроме архива на диске, в памяти целиком;
- один архив под разными URI (URI 4, «Прочие пределы») — и для памяти два архива.

Ц6, любой архив. Архив не на диске читается через workspace.fs — схема любая, в том числе
"zip-document" (URI Т5). Пределы:
- архив не на диске — в памяти целиком, не больше maxInMemoryArchiveSize;
- вложенный архив — ещё и не больше maxEntrySize: он данные записи внешнего; без наблюдения
  внешняя запись распаковывается заново на каждый вызов;
- файловая система архива должна давать stat и readFile; наблюдение за ресурсом — для событий
  (Ц3).

Ц7, отказ. FileNotFound — ровно когда файла нет (3.2): существование вызывающие проверяют именно
по нему. Остальные отказы — с причиной в сообщении; закреплены ещё FileNotADirectory (3.5) и
NoPermissions для записи (3.7), прочие виды не обещаны [Р2].

Ц8, по правилам VS Code. FileStat: mtime растёт с изменением архива (3.3), size равен длине
содержимого той же версии (3.3, 3.4, 3.10). Событие — после смены версии (3.6). Только чтение —
регистрацией (3.1) и NoPermissions (3.7).

Чего от провайдера не ждать:
- каталогов: FileType.Directory, readDirectory, неявных каталогов, открытия архива папкой [Р1];
- содержимого файлов записи-каталога и корня по этому документу: его задаёт расширение каждой
  реализации (3.10), и у разных реализаций оно может быть разным; что делать с данными
  записи-каталога, если они в архиве всё же есть, решает тоже расширение;
- символьных ссылок: FileType.SymbolicLink не бывает, цель не разрешается [Р13];
- сведений о записи сверх размера: дата записи, права, комментарий, extra-поля, метод в FileStat не
  попадают; mtime — архива, не записи [Р3];
- исправления URI, поиска записи по похожему имени, отождествления архивов (URI 3.4, [URI Р4]);
- событий по URI без наблюдения, событий раньше смены версии, срока событий; Changed только тем
  файлам, содержимое которых изменилось;
- данных по частям: readFile отдаёт файл целиком, в памяти; данных сверх предела; вопросов
  пользователю, пароля;
- восстановления повреждённых архивов и одинакового решения разных реализаций о том, читается ли
  повреждённый архив;
- вида отказа, кроме FileNotFound, FileNotADirectory и NoPermissions; текста отказа;
- того, что запись из одной версии будет в следующей под тем же URI с теми же данными: index —
  позиция среди одноимённых (URI 2);
- согласованности со списком редактора архива сильнее общей версии: пока одна из сторон не узнала
  об изменении архива, список и вкладка могут быть по разным версиям;
- времени отклика: оно растёт с размером центрального каталога и записи-файла.


5. Обоснования

Почему правила раздела 3 такие. Наблюдения, на которые они опираются, — раздел 6; отклонённое —
раздел 8.

Р1. Каждый объект архива — файл; каталогом не становится ни один.
    - Формат адресует объекты, а не пути [URI Р12]. Иерархия потребовала бы правил для
      дубликатов, "..", записи-файла "a" рядом с записью-каталогом "a/" — и часть записей стала
      бы недостижимой.
    - Запись-каталог и корень — не каталоги. Будь они FileType.Directory, VS Code не открыл бы
      их во вкладке, а на readDirectory пришлось бы отвечать. Ответ без потомков — неправда, с
      потомками — неисполним: потомка VS Code адресует Uri.joinPath от URI каталога, а такой URI
      неканоничен — метка расходится с entry — и получит отказ. [О1, О2]
    - Отказ readDirectory — FileNotADirectory, как у любого файла: его понимают без пояснений.

Р2. FileNotFound — ровно когда файла нет; прочие виды отказов не обещаны.
    - FileNotFound в API значит «uri doesn't exist» (6.1), и по нему вызывающие решают, есть ли
      ресурс. Отказ FileNotFound для записи, которая есть, но не читается, сказал бы, что её нет;
      ошибка файловой системы архива, кроме FileNotFound, тоже не «нет»: архив, возможно, есть.
    - Неканонический URI — FileNotFound: для VS Code это ресурс, которого нет, и ответить так
      можно, ничего не читая. Вид отказа формат оставил провайдеру [URI Р11].
    - Остальным видам (7) никто, кроме показа, смысла не придаёт; закреплять их — та же лишняя
      часть контракта, что код отказа в формате [URI О15]. FileNotADirectory и NoPermissions
      закреплены, потому что их значение API описывает для этих самых случаев. [О9]
    - watch на неканонический URI не бросает исключения: что VS Code с ним делает, не проверено
      (6.3), а наблюдение, которое ничего не сообщает, — отказ без последствий.

Р3. mtime и ctime — архива, а не записи.
    - API требует, чтобы после события mtime вырос, иначе VS Code может не перечитать редактор
      (6.1). Дата записи этого не обещает: инструменты воспроизводимой сборки ставят всем записям
      одну дату (1980-01-01, SOURCE_DATE_EPOCH), и изменённая запись осталась бы с прежней.
      mtime архива растёт при каждой его перезаписи.
    - Дата записи в ZIP — местное время без часового пояса с шагом 2 с; точные метки — в
      необязательных extra-полях. В миллисекунды UTC её однозначно не перевести.
    - Цена — после изменения архива перечитываются все открытые из него вкладки (4, Ц3). Дату
      записи показывает редактор архива. [О3]

Р4. Сверка — по центральному каталогу.
    - Запись — запись центрального каталога [URI Р2]; флаги, метод, размеры и CRC-32 — её
      сведения. Локальный заголовок может расходиться с центральным каталогом, а при бите 3 (data
      descriptor) размеров и CRC-32 в нём нет вовсе; из него нужна только его собственная длина
      (probes/fake-data-descriptor — архив, который поточный разбор по локальным заголовкам
      читает неверно).
    - Проверяются и размер, и CRC-32: размер — от бомбы и обрыва, CRC-32 — от порчи и смеси
      версий. Несверенное не отдаётся: вызывающий не отличит неполные данные от настоящих.
    - Распаковка обрывается на заявленном размере: память на запись ограничена тем, что уже
      сверено с пределом, какой бы ни была степень сжатия.

Р5. stat не решает, отдаст ли данные readFile.
    - Зашифрованная запись существует. FileNotFound в stat сказал бы, что её нет; другой отказ —
      что не получить даже сведений, хотя они есть. Отказывает та операция, которая не может
      выполниться, — readFile, и VS Code показывает его причину во вкладке (не проверено, 6.3).
    - stat вызывают часто, и он не читает данных.

Р6. Между вызовами архив не открыт.
    - Открытый файл на Windows, в зависимости от режима открытия и версии системы, может мешать
      удалить или заменить его; сборка, пересобирающая архив, пока открыта вкладка, падала бы.
      Без открытого дескриптора вопроса нет ни на какой системе, и проверять его не нужно (6.3).
    - Цена — открытие файла на каждый readFile; это дешевле чтения данных. Согласованность не
      страдает: открытый файл сверяется с версией, по которой разобран центральный каталог (7),
      а данные — по CRC-32 (Р4). [О4]

Р7. Память — пока наблюдают.
    - Владелец известен: наблюдение живёт, пока открыта вкладка, и освобождается вместе с ней
      (6.1).
    - Без наблюдения владельца нет. Несколько секунд покрывают stat, readFile и watch одного
      открытия, идущие подряд, а фоновое чтение многих архивов другим расширением не копит память.
      [О12]

Р8. Версия сверяется при каждом вызове.
    - Тогда свежесть одна для всех вызовов и не зависит от того, сообщает ли файловая система
      архива об изменениях: вызов отвечает по тому, что на месте сейчас. Цена — один stat архива
      на вызов (у архива на диске при readFile — fstat уже открытого файла).
    - Признак версии — mtime и size: их даёт stat любой файловой системы, и по ним же VS Code сам
      решает, изменился ли файл (FileStat, 6.1). Сравнивать содержимое — читать архив целиком. [О5]

Р9. События — по существованию; Changed — всем, кто есть в обеих версиях.
    - mtime у такой записи вырос (Р3): по правилам API это изменение, о нём и сообщается.
    - Узнать, что данные те же, не читая их, нельзя: совпадение заявленных CRC-32 и размеров —
      признак, а не доказательство, а пропущенное событие оставило бы вкладку со старыми данными.
      [О6]
    - Created — запись вернулась в пересобранный архив: вкладка, помеченная удалённой, снова
      показывает данные.
    - Новая версия — до события: VS Code по событию сразу вызывает stat и readFile, и они должны
      ответить уже по ней.

Р10. Нечитаемая версия — не версия.
    - Архив пишется не мгновенно: пока инструмент пишет, файл обрезан, центрального каталога в
      конце нет. Отвечай провайдер на это Deleted, при каждой пересборке все вкладки архива мигали
      бы «удалён». Ждать следующего изменения — верный ответ для частого случая. [О7]
    - Цена — для редкого: архив навсегда заменён не-ZIP, вкладки показывают последние данные, а
      повторное открытие откажет с причиной (4, Ц3).

Р11. Пределы жёсткие и только в настройках пользователя.
    - readFile вызывают и в обход редактора архива: восстановление вкладок, другие расширения,
      чтение вложенного архива. Предел, который проверял бы только редактор, обходился бы, и
      запись с заявленными 4 ГиБ выделилась бы в памяти extension host.
    - Спрашивать подтверждение нельзя: окно всплывало бы и от фонового чтения. [О8]
    - Рабочая область — такие же недоверенные данные, как архив: репозиторий не должен поднимать
      пределы своими настройками, поэтому scope "machine".
    - Нужен больший предел — пользователь меняет настройку; сообщение отказа её называет.
    - Для архива на диске предел памяти — на центральный каталог: каталог в сотни мегабайт —
      миллионы записей, и разобранный он занимает ещё больше.

Р12. Архив на диске — произвольным доступом, прочие — целиком.
    - Архив в гигабайты открывается за время чтения центрального каталога, а память — по нему и
      записи, не по архиву.
    - workspace.fs отдаёт файл только целиком: у архива не на диске другого чтения нет. Поэтому
      для него — предел на размер.
    - "file" — схема, которую провайдер может читать с диска сам: при extensionKind "workspace"
      он работает на том хосте, где лежат файлы, в том числе в Remote.

Р13. Ничего сверх записи.
    - Символьная ссылка в ZIP — запись-файл, данные которой — путь цели. Разрешение потребовало бы
      правил путей, которых у ZIP нет [URI Р12], и могло бы увести за пределы архива. Данные ссылки
      — её текст, как у любой записи. [О10]
    - Вложенный архив раскрывается только по URI, который кто-то построил: самораскрытие (архив в
      архиве в архиве, архивы-квайны) — работа, которой никто не просил.

Р14. Недоверенная рабочая область.
    Провайдер ничего не исполняет и не пишет и рассчитан на недоверенный архив (Ц4); выключать его
    в ограниченном режиме — лишать пользователя безопасного просмотра.

Р15. Повреждённый архив не восстанавливается.
    Восстановление — поиск локальных заголовков, угадывание смещений — отдало бы записи, которых
    нет в центральном каталоге, или данные, которых архив не заявляет, и разошлось бы со списком
    редактора архива. Восстанавливать — дело внешних инструментов. [О11]

Р16. Один к одному — только запись-файл; запись-каталог и корень — расширение.
    - Один к одному отдаётся то, что в архиве есть как данные, — данные записи-файла. У
      записи-каталога данных нет: APPNOTE их запрещает (4.3.8); центральный каталог — сведения
      о записях, а не данные. Любые байты для них — представление, то есть выбор, а не
      извлечение, и в этот документ он не входит.
    - На что опираются VS Code и вызывающие — существование, тип, версия, события,
      FileNotFound, — задано здесь и для этих файлов (3.10): расширение задаёт содержимое, но
      контракта не меняет.
    - Требование к самому документу — потому что повторяемости от провайдера не требуется («Как
      читать»): без расширения содержимое этих файлов было бы просто поведением кода. [О13]


6. Проверка

6.1 Что наблюдалось

probes/uri-roundtrip (VS Code 1.145.2, Linux):
- vscode.open вызывает у провайдера stat, readFile и watch; openTextDocument — stat и readFile,
  watch не вызывает;
- watch — один на URI, сколько бы редакторов его ни показывали (splitEditor, третья группа);
  options — recursive false, excludes пустой; освобождение — после закрытия последнего редактора;
  тот же path с другим query — отдельный watch.

Повторная регистрация схемы — исключение (URI 6.1).

Документация API (@types/vscode 1.95): FileNotFound — «when uri doesn't exist» у stat, readFile,
readDirectory; после события mtime и size должны быть обновлены, иначе редактор может не показать
изменение; FilePermission.Readonly — у всех FileStat провайдера с isReadonly: true; наблюдение за
одним файлом — RelativePattern(<URI файла>, "*").

6.2 Что проверить у реализации

По разделу 3, на каждый пункт — тест.
- URI: неканонические формы из URI 3.4 — FileNotFound у stat, readFile, readDirectory без единого
  чтения архива (счётчик чтений); watch — без событий и без исключения.
- Существование: нет архива, нет записи, index не меньше числа одноимённых — FileNotFound; архив
  не ZIP, обрезанный, ресурс архива — каталог, ошибка файловой системы архива — отказ другого
  вида. URI корня: архив есть и читается как ZIP — файл есть, даже без записей; нет архива —
  FileNotFound.
- Трудные имена: дубликаты (probes/duplicate-names), пустое имя (probes/empty-name), конфликты
  путей (probes/path-conflicts), байты вне UTF-8, "C:/x" — каждая запись по своему URI отдаёт свои
  данные.
- stat: FileType.File у записи-файла, записи-каталога, корня и символьной ссылки; size равен
  длине readFile у каждого из них; mtime — mtime архива; stat зашифрованной записи успешен.
- readDirectory: FileNotADirectory у записи-файла, записи-каталога и корня.
- readFile: stored, deflate, ZIP64, data descriptor (probes/fake-data-descriptor). Отказы 1–3 — до
  чтения данных (счётчик): зашифрованная запись, методы 9, 12, 14, 93, размер сверх предела.
  Бомба: заявлено 1 КиБ, распаковывается 1 ГиБ — отказ, память не выше заявленного. Распаковано
  меньше заявленного; испорчен байт данных — отказ по CRC-32. Локальный заголовок с другими
  методом и размерами — читается по центральному каталогу.
- Объём чтения архива на диске: чтение центрального каталога — не больше его размера + 65 557 + 76
  байт (EOCD с наибольшим комментарием, локатор и запись ZIP64 EOCD); readFile — только локальный
  заголовок и сжатые данные записи.
- Ресурсы: после каждого вызова у процесса нет открытого дескриптора архива; архив, из которого
  открыта вкладка, удаляется и заменяется на Linux, Windows и macOS; без наблюдения память
  отпущена через несколько секунд.
- События: запись изменилась — Changed, и readFile по событию — новые данные; удалена — Deleted;
  добавлена — Created; архив удалён — Deleted всем, создан снова — Created; архив пишется
  (обрезанный файл) — событий нет, по завершении — Changed; две вкладки одного URI — одно событие.
- Вложенный архив: чтение записи, события при изменении внешнего архива, оба предела.
- Операции записи — NoPermissions.
- Расширение: реализация называет его; содержимое записи-каталога и корня проверяется по нему.
- Пределы: изменение настройки действует без перезагрузки; настройка рабочей области не действует.
- Активация: вкладка с URI записи восстанавливается после перезагрузки окна.

6.3 Не проверено

На что контракт опирается, но что не проверялось:
- как VS Code показывает отказ readFile разных видов и как открытая вкладка ведёт себя после
  Deleted и последующего Created;
- что VS Code пропускает перечитывание при тех же mtime и size, — известно из документации, не из
  пробы;
- что VS Code делает с исключением из watch — поэтому watch не бросает (Р2);
- RelativePattern(<URI файла>, "*") для архива вне рабочей области, для архива, которого ещё нет,
  и для URI "zip-document" (вложенный архив);
- поведение Windows с открытым дескриптором — Р6 сделан так, чтобы оно не имело значения;
- восстановление вкладок после перезагрузки окна, Remote, VS Code for the Web (URI 6.6);
- URI корня в VS Code: доходит ли он до провайдера без изменений и как показана вкладка
  (URI 6.6).


7. Заметки по реализации

Как сделать и что учесть. Может устаревать независимо от контракта.

- URI: построение и разбор — один модуль с генератором, по probes/uri-format/uri.js (URI 7).
  Разбор возвращает тройку, корень или ничего; ничего — FileNotFound(uri), без чтения.
- Читатель центрального каталога — общий с редактором архива: иначе запись из списка редактора
  может не найтись провайдером.
- Индекс — словарь: байты имени → записи с этим именем в порядке центрального каталога. Имена —
  байты, не строки: никакого декодирования, нормализации, замены "\" на "/".
- yauzl, если читатель — он: decodeStrings: false — имена приходят буферами, как в центральном
  каталоге; при true yauzl декодирует их (бит 11, 0x7075) и проверяет validateFileName, а запись
  должна находиться по байтам [URI Р2]. CRC-32 yauzl не сверяет. Зашифрованную запись и прочие
  методы openReadStream отвергает нетипизированной ошибкой — проверять до вызова (шаги 1–2).
  validateEntrySizes: true — сверка распакованного размера.
- Данные — по смещению из индекса, без повторного разбора центрального каталога. Архив на диске:
  open, fstat дескриптора (не stat пути: между ними файл могут заменить), сверка mtime и size с
  версией индекса, чтение, close в finally. Не совпало — перечитать центральный каталог, ответить по
  новой версии и разослать события, как при событии наблюдателя.
- Распаковка — zlib inflateRaw потоком, со счётчиком: превысил заявленное — оборвать. CRC-32 —
  zlib.crc32, где он есть, иначе buffer-crc32 (зависимость yauzl). Разбор большого центрального
  каталога и распаковка — асинхронно, не занимая extension host надолго.
- Шифрование — бит 0 флагов; его ставят и традиционное шифрование, и сильное (бит 6), и WinZip
  AES (метод 99).
- Наблюдение за архивом — workspace.createFileSystemWatcher(new RelativePattern(<URI архива>,
  "*")), один на архив, пока есть наблюдения за его URI. onDidChange, onDidCreate, onDidDelete →
  перечитать; если перечитывание уже идёт — ещё одно после него, не параллельно.
- Одновременные вызовы по одному архиву ждут одного чтения центрального каталога (общий
  Promise).
- Не держать блокировок через await: workspace.fs.readFile(P) вложенного архива приходит в этот
  же провайдер.
- Виды отказов, не закреплённые контрактом: запись есть, но не отдаётся (шифрование, метод,
  предел) — NoPermissions; архив не читается как ZIP, повреждён, данные не сошлись с заявленным —
  Unavailable; ошибка файловой системы архива — её же вид, с сообщением про архив. В сообщении —
  метка записи (uri.path) и причина.
- package.json: activationEvents ["onFileSystem:zip-document"] (onCustomEditor редактора архива
  VS Code выводит сам, onFileSystem — нет); capabilities.untrustedWorkspaces.supported: true;
  настройки 3.9 в contributes.configuration со scope "machine".
- Срок памяти без наблюдения — например, 5 с с последнего вызова по архиву.


8. Отклонённые варианты

О1 (Р1). Запись-каталог или корень — FileType.Directory. VS Code не открывает их во вкладке, и
    на readDirectory нечего ответить.

О2 (Р1). readDirectory со списком: потомки по префиксу имени — их URI от Uri.joinPath
    неканоничны, а свои URI потомков VS Code из списка не возьмёт; пустой список — неправда о
    записи, у которой есть потомки.

О3 (Р3). mtime — дата записи: не растёт при воспроизводимой сборке, местное время без пояса.

О4 (Р6). Держать дескриптор, пока наблюдают, — снимок старой версии при атомарной замене. Мешает
    удалять и заменять архив на части систем, а снимок нужен только до события.

О5 (Р8). Доверять одному наблюдателю, без сверки при вызове: на файловых системах без наблюдения
    вкладки и workspace.fs отвечали бы по старой версии сколько угодно долго.

О6 (Р9). Changed только записям, у которых изменились заявленные CRC-32, размеры или смещение:
    признак, не доказательство, а mtime вырос у всех.

О7 (Р10). Нечитаемая версия — Deleted всем записям: мигание «удалён» на каждой пересборке.

О8 (Р11). Подтверждение для записи сверх предела: всплывало бы от фонового чтения и
    восстановления вкладок.

О9 (Р2). Закрепить вид каждого отказа: часть контракта, на которую никто не опирается.

О10 (Р13). Разрешать символьные ссылки: правила путей, которых у ZIP нет, и выход за архив.

О11 (Р15). Восстанавливать повреждённые архивы: данные, которых архив не заявляет, и расхождение со
    списком редактора.

О12 (Р7). Кэш без наблюдения — без срока или по объёму памяти: память без владельца, и фоновое
    чтение архивов её копит.

О13 (Р16). Запись-каталог — один к одному, как запись-файл (редакция 1). Данных у неё по APPNOTE
    нет, и это дало бы пустой файл: содержимое, которое стоит показать, — выбор, а не данные
    архива.

Отложено, не отклонено.

Произвольный доступ к вложенному архиву без сжатия (метод 0): читать его кусками из внешнего, а не
    целиком в память.

Методы сжатия сверх 0 и 8 — Deflate64 (9), bzip2 (12), LZMA (14), Zstandard (93): набор растёт без
    новой редакции (3.4).

Относительные ссылки между записями (Markdown в архиве ссылается на "./img.png"): не провайдер — он
    отвечает только по каноническим URI [URI Р7]; если делать, то слоем выше, с явным правилом
    разрешения и отказом при неоднозначности.
