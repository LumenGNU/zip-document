# Zip Document — спецификация

Статус: **черновик v0.2**. **!ПРИНЯТ НЕ БУДЕТ!**
Разделы с пометкой ❓ — открытые вопросы, требуют решения.

## 1. Цель

Открывать ZIP-архив в VS Code как обычный документ: `.zip`, выбранный в Explorer, показывает
содержимое архива (список файлов с метаданными), из которого любой файл можно открыть
в редакторе VS Code — без распаковки на диск.

## 2. Сценарии использования

1. **Просмотр.** Пользователь открывает `release.zip` → видит вкладку со списком файлов и их
   метаданными (§5).
2. **Открытие файла.** Переход по ссылке на файл → он открывается в обычном редакторе VS Code в режиме
   только для чтения.
3. **Обновление.** Если `.zip` на диске изменился — представление и открытые файлы перечитываются автоматически.

## 3. Не входит в v1 (non-goals)

- Изменение архива (добавление, удаление, переименование, редактирование файлов).
- Зашифрованные записи (показываются в списке с пометкой, открыть нельзя).
- Методы сжатия кроме stored (0) и deflate (8) — Deflate64, bzip2, LZMA, Zstd… (записи показываются в
  списке с пометкой, открыть нельзя).
- Архивы, где имя записи начинается с `/` или `X:/` или содержит сегмент `..` (архив не
  открывается, §4.2).
- Форматы кроме ZIP (tar, 7z, rar).
- Многотомные (split/spanned) архивы.
- VS Code for the Web (vscode.dev, github.dev). Целевая платформа — только десктоп
  (локально и Remote-SSH/WSL/Dev Containers, где расширение работает на стороне хоста с файлами).

Свойства этой структуры:

- **Провайдеры не вызывают друг друга.** ZipEditorProvider попадает в ZipFileSystemProvider только
  через VS Code, как любой другой код с `zip:`-URI: открывая запись (2 → 3), читая архив с `zip:`-URI
  (7 → 3), наблюдая за ним (2 → 3). Связывает их формат `zip:`-URI (§4.3): ZipEditorProvider URI
  строит, ZipFileSystemProvider разбирает. Пути записей в URI и в списке webview одни и те же —
  из `ZipArchive.index`.
- **ZipReader отвечает на «дай мне архив»**: `open(<URI архива>, { maxInMemorySize })` возвращает
  открытый `ZipArchive`. Сколько его держать и когда закрыть, решает получивший (§4.4, §4.5). Сам ZipReader между
  вызовами ничего не хранит.
- **Защиты и ограничения при чтении записи — в одном месте**, `ZipArchive.read()` (§4.2), какой бы
  путь к нему ни вёл.
- **Схема URI архива нигде не разбирается, кроме выбора способа открытия в `ZipReader` (§4.1).**
  Чтение — `workspace.fs`, наблюдение — `createFileSystemWatcher`, для любой схемы; как их
  реализует файловая система, в том числе наша собственная для `zip:`, — её дело.
- **Композиция** — в `activate()`: регистрирует оба провайдера:
  `registerFileSystemProvider('zip', …, { isReadonly: true, isCaseSensitive: true })` (имена в ZIP
  регистрозависимы) и `registerCustomEditorProvider('zipDocument.viewer', …)`.

### 4.1 ZipReader
- Единственная операция — `open(<URI архива>, { maxInMemorySize })` → `ZipArchive` (§4.2): выбрать
  способ открытия по схеме URI, открыть `yauzl.ZipFile` и передать его `ZipArchive.fromZipFile`
  (§4.2), которая читает центральный каталог и строит пути записей. Состояния между вызовами нет;
  закрывает архив получатель. Лимит приходит параметром: настройки `ZipReader` не читает.
- Задача `ZipReader` — всё, что зависит от VS Code и схемы URI: способ доступа к байтам архива
  и лимит на чтение в память. Состав архива — дело `ZipArchive`, от VS Code не зависящего.
- Способ открытия зависит от схемы URI архива:
  - `file:` — `yauzl.open(path)`: `yauzl` держит открытый дескриптор и читает по смещениям, архив
    целиком в память не загружается;
  - прочие схемы (в т. ч. `zip:`) — `workspace.fs.readFile` целиком в память, затем
    `yauzl.fromBuffer`. Чтение по частям здесь невозможно: `workspace.fs` отдаёт файл только
    целиком. Перед чтением размер из `workspace.fs.stat` сверяется с `maxInMemorySize`:
    больше — `TooLarge` (§9 п. 7).
- Опции `yauzl` одинаковы для обоих способов, поэтому дальше источник не различается:
  - `lazyEntries: true` — центральный каталог читается по требованию, данные записей не трогаются;
  - `autoClose: false` — `ZipFile` остаётся открытым после чтения каталога, до `ZipArchive.close()`;
  - `decodeStrings: true`, `strictFileNames: false` (умолчания) — декодирование имён и комментария
    (§4.2) выполняет `yauzl`, некорректные имена (§4.2) отвергает его `validateFileName`;
  - `validateEntrySizes: true` — см. `ZipArchive.read()`.
- Если `yauzl` отверг архив при открытии — ошибка структуры в конце архива (EOCD, ZIP64 EOCD), —
  `ZipArchiveError` `Corrupt` с сообщением `yauzl`. `ZipFile` не создан, закрывать нечего.
- Ошибки чтения каталога `fromZipFile` обрабатывает сама и закрывает `ZipFile` (§4.2); `ZipReader`
  их только пропускает дальше.

### 4.2 ZipArchive
Открытый архив. Обёртка над `yauzl.ZipFile`, держит его открытым до `close()`. Задачи: чтение
центрального каталога, единый вид состава архива независимо от источника и чтение записи
с защитами и ограничениями (§7). От VS Code не зависит: лимиты приходят параметрами, ошибки — свои
(`ZipArchiveError`, см. ниже); перевод их в `FileSystemError` или сообщение в webview — у вызывающих.

**Создание** — `ZipArchive.fromZipFile(zipFile)`, асинхронная фабрика (`yauzl` с `lazyEntries`
отдаёт записи каталога по одной через `readEntry`). `zipFile` должен быть открыт с опциями §4.1.
В коде расширения её вызывает только `ZipReader.open()`; тест §6 вызывает её напрямую с `ZipFile`
из `yauzl.fromRandomAccessReader` со счётчиком байт (в коде расширения `RandomAccessReader` не
используется).
- Центральный каталог читается один раз, целиком, до того как архив отдан; дальше состав не
  меняется. ZIP64 — средствами `yauzl`. Для каждой записи составляется описание (поля — «Состав»),
  затем строится `index` (правила — «Пути записей»).
- `ZipFile` переходит во владение фабрики. Если `yauzl` отверг запись каталога — ошибка структуры
  (смещения, размеры) или некорректное имя (его `validateFileName`, правила — «Пути записей»), —
  фабрика закрывает `ZipFile` и бросает `Corrupt` с сообщением `yauzl`: получателю отдавать нечего.
  После успешного создания `ZipFile` закрывается только через `close()`.

**Состав** — неизменен, пока архив открыт:
- `comment` — комментарий архива, декодированный как CP437;
- `entries` — записи в порядке центрального каталога. Для каждой:
  - `name` — имя записи: UTF-8 по флагу 0x800, иначе CP437, приоритет у Unicode Path (0x7075);
    `\` считается разделителем и заменяется на `/`;
  - `compressedSize`, `uncompressedSize`, `crc32`;
  - `modified` — `entry.getLastModDate()` (учитывает расширенные метки времени, `yauzl` ≥ 3.2.0);
  - `method`, `encrypted` (бит 0 флагов);
  - `readable` — пройдёт ли запись проверки 1–2 из `read()`; по нему список помечает записи, которые
    открыть нельзя (§5);
  - непрозрачная ссылка на `yauzl.Entry` для `read()`;
- `index` — пути записей: путь → запись или каталог, плюс записи, оставшиеся без пути (правило ниже).

**Пути записей** (`index`). Путь строится из `name`, обоснование — §9 п. 5:
- имя, которое начинается с `/` или `X:/` или содержит сегмент `..`, некорректно: архив не
  открывается (`fromZipFile` → `Corrupt`), даже из-за одной такой записи;
- в остальных `posix.normalize` убирает пустые сегменты и `.`: `./a//b` → `a/b`. Имя, от которого
  ничего не осталось (`./`), претендует на корень, а корень — каталог (см. конфликты ниже);
- каталоги — явные записи (имя оканчивается на `/`) и неявные: префиксы путей других записей
  (`a/b/c` без `a/` и `a/b/` даёт каталоги `a` и `a/b`);
- один путь — одна запись. Если на путь претендуют несколько записей, его получает одна:
  при дубликатах — первая по порядку в центральном каталоге, при конфликте файл/каталог —
  каталог. Остальные записи видны в списке (§5), но URI у них нет и открыть их нельзя.

**`read(entry, { maxSize })`** → `Uint8Array`. `yauzl` распаковывает ровно stored и deflate (§3),
а зашифрованную запись и прочие методы его `openReadStream` отвергает нетипизированной ошибкой,
поэтому `read()` проверяет их сам до вызова (шаги 1–2) и отдаёт свой код. До чтения данных:
1. запись зашифрована → `Encrypted`;
2. метод сжатия не поддерживается (§3) → `UnsupportedMethod`;
3. `uncompressedSize > maxSize` → `TooLarge`.

Во время чтения (`openReadStream`):
4. буфер выделяется ровно по `uncompressedSize`; `validateEntrySizes` обрывает поток, как только
   распаковано больше заявленного, и проверяет, что в конце не меньше → `Corrupt`. Поэтому память на
   запись не превышает заявленного размера, который уже проверен на шаге 3, — это и есть защита от
   zip-бомбы: степень сжатия значения не имеет;
5. CRC-32 распакованных данных сверяется с `crc32` из центрального каталога (`yauzl` этого не
   делает) → `Corrupt`. Считается `buffer-crc32` — он уже зависимость `yauzl`, объявляем его своей
   зависимостью явно.

**`close()`** — `ZipFile.close()`: для `file:` закрывает дескриптор, для буфера отпускает память.
Повторный `close()` ничего не делает; `read()` после `close()` — неправильное использование (§4).

**Время жизни** определяет владелец (§4.4, §4.5). Что из него следует:
- для `file:` открыт дескриптор файла. Если архив атомарно заменят (запись в новый файл +
  rename), `ZipArchive` продолжит читать старую версию — целиком и согласованно — пока владелец
  по событию наблюдателя не откроет новый и не закроет старый;
- для прочих схем в памяти лежит весь архив.

Ошибки `ZipArchiveError` — по коду:

| Код                 | Когда                                                                   |
|---------------------|-------------------------------------------------------------------------|
| `Encrypted`         | `read()`: запись зашифрована                                            |
| `UnsupportedMethod` | `read()`: метод сжатия не поддерживается (§3)                           |
| `TooLarge`          | `read()`: `uncompressedSize > maxSize`; `ZipReader.open()`: архив не на `file:` больше `maxInMemorySize` |
| `Corrupt`           | `ZipReader.open()`: ошибка структуры EOCD; `fromZipFile`: ошибка структуры каталога или некорректное имя записи; `read()`: размер или CRC-32 |

### 4.3 Формат `zip:`-URI
Отношение, а не компонент: по нему ZipEditorProvider и любой другой код адресует запись архива
(связь 2), а ZipFileSystemProvider её находит (связь 3).
- `zip:/<путь внутри архива>?<encoded URI архива>`,
  например `zip:/src/main.ts?file%3A%2F%2F%2Fhome%2Fu%2Frelease.zip`.
- Путь внутри архива — путь записи из `ZipArchive.index` (§4.2). Это нормальный `path`, поэтому
  заголовок вкладки, языковой режим и иконка определяются по имени файла.
- URI архива — любой, в том числе `zip:`-URI записи другого архива.

### 4.4 ZipFileSystemProvider
- Схема `zip`, `isReadonly: true`, `isCaseSensitive: true`. Формат URI — §4.3.
- Время жизни архива (§9 п. 8):
  - `ZipArchive` архива держится, пока есть хоть один `watch` на его URI (открытые вкладки,
    наблюдатели): первый `watch` — `ZipReader.open`, `dispose` последнего — `close()`;
  - вызов для архива без наблюдения (например, `stat` до первого `watch`, фоновое чтение другим
    расширением) — `ZipReader.open` → операция → `close()`.
- `stat` / `readDirectory` — по `ZipArchive.index`; `readFile` — запись по пути из `index` →
  `ZipArchive.read`. Путь без записи (неявный каталог, проигравшая в конфликте, §4.2) у `readFile` —
  `FileSystemError.FileNotFound`, у `stat` неявный каталог — `FileType.Directory`.
- Лимиты (§9 п. 7): `ZipReader.open` получает `maxInMemorySize = zipDocument.maxInMemoryArchiveSize`,
  `readFile` передаёт `ZipArchive.read()` `maxSize = zipDocument.maxEntrySize`. Запись больше лимита не открывается и ничего не спрашивает: `TooLarge` →
  ошибка с размером записи и именем настройки; VS Code показывает её во вкладке.
- Ошибки `ZipArchiveError` (§4.2) → `FileSystemError` с текстом по коду: `Encrypted`,
  `UnsupportedMethod`, `TooLarge` — `NoPermissions`; `Corrupt` — `Unavailable`.
- `FileStat` записи и каталога (§9 п. 6): `mtime` и `ctime` — `mtime` архива (`workspace.fs.stat`
  URI архива), `size` — исходный размер
  записи (у каталога — 0). Собственная дата записи в `FileStat` не попадает, она показывается только
  в колонке «Изменён» (§5).
- Операции записи бросают `FileSystemError.NoPermissions`.
- Активация — `onFileSystem:zip` в `activationEvents`. Провайдер файловой системы не является
  contribution, поэтому неявного события активации для него нет; без явного VS Code после
  перезагрузки окна восстановит вкладки с `zip:`-URI раньше, чем расширение зарегистрирует схему,
  и покажет ошибку. (`onCustomEditor:zipDocument.viewer` выводится из `contributes.customEditors`
  автоматически.)
- Отслеживание изменений (сценарий 3). VS Code вызывает `watch(uri, options)` для открытых вкладок
  и для наблюдателей, созданных на `zip:`-URI. Провайдер подписывается на архив этого URI —
  `workspace.createFileSystemWatcher(new RelativePattern(<URI архива>, '*'))`, один наблюдатель на
  архив, сколько бы URI из него ни наблюдалось. При изменении архив открывается заново
  (`ZipReader.open`), для каждого наблюдаемого URI этого архива по новому `index` отправляется
  `onDidChangeFile`, после чего новый `ZipArchive` заменяет старый, а старый закрывается:
  - запись есть в новом архиве — `Changed` (VS Code перечитает открытый редактор);
  - записи больше нет — `Deleted`;
  - удалён сам архив — `Deleted` для всех его URI, старый `ZipArchive` закрывается.

### 4.5 ZipEditorProvider
- `CustomReadonlyEditorProvider`, viewType `zipDocument.viewer`. Селекторы (§9 п. 4):
  - `*.zip` — `priority: "default"`;
  - прочие форматы на основе ZIP — `priority: "option"`, доступны через «Open With…»:
    `*.jar`, `*.war`, `*.ear`, `*.aar`, `*.apk`, `*.aab`, `*.ipa`, `*.vsix`, `*.nupkg`, `*.whl`,
    `*.xpi`, `*.epub`, `*.docx`, `*.xlsx`, `*.pptx`, `*.odt`, `*.ods`, `*.odp`, `*.kmz`.
- Время жизни архива (§9 п. 8) — время жизни документа: `openCustomDocument` → `ZipReader.open`
  (`maxInMemorySize = zipDocument.maxInMemoryArchiveSize`, §9 п. 7), `ZipArchive` хранится в
  `CustomDocument`, `dispose` документа → `close()`. Данные записей в v1 редактор сам не читает
  (запись открывается через `vscode.open`), архив держится ради `index` (список) и будущего
  «Сохранить как…» (§5).
- Список записей — из `ZipArchive.entries` / `index`, передаётся в webview сообщением `entries`
  (связь 5).
- Сообщение `open(path)` → `vscode.commands.executeCommand('vscode.open', <zip:-URI записи>)` (§4.3).
- Изменение архива — `workspace.createFileSystemWatcher(new RelativePattern(<URI документа>, '*'))`:
  при `onDidChange` — `ZipReader.open` заново, webview получает новый `entries`, старый `ZipArchive`
  закрывается; при `onDidDelete` или ошибке открытия — старый закрывается, webview получает `error`.
- `extensionKind: ["workspace"]` — в Remote-сессиях расширение работает на удалённом хосте,
  где лежат файлы, поэтому прямое открытие файла через `yauzl.open` остаётся корректным.

## 5. Интерфейс представления

- Шапка: имя архива, число файлов, суммарный размер (исходный / сжатый), комментарий архива, если есть.
- Колонки: Имя, Размер, Изменён. Сортировка по выбранной колонке.
- Запись показывается под своим путём (§4.2). Записи, которые открыть нельзя (без URI или
  `readable = false`, §4.2), помечены и ссылками не являются.
- Строгий CSP, без внешних ресурсов.

### Заложить возможность, но не требуется реализация в v1
- Фильтр по имени (поле поиска сверху).
- Иконки: 🔒 для зашифрованных записей, отличие каталогов от файлов.
- Клавиатура: перемещение по списку стрелками.
- Контекстное меню: Открыть, Открыть сбоку, Сохранить как…, Копировать путь.
- Оформление только через CSS-переменные темы VS Code (`--vscode-*`).

## 6. Производительность

- Требования по времени в v1 не задаются: замер в extension host ненадёжен (шум CI-машин, холодный
  и тёплый дисковый кэш, рендер webview из exthost не наблюдаем). Вместо этого — проверяемое
  структурное требование:
  - **при открытии архива читаются только хвост файла и центральный каталог**: прочитанный объём
    не превышает `размер CD + 65 557 + 76` байт (хвост файла с EOCD и максимальным комментарием +
    ZIP64-локатор и ZIP64 EOCD). Проверяется юнит-тестом `ZipArchive.fromZipFile` на архиве
    с большими записями: в тесте `ZipFile` создаётся через `yauzl.fromRandomAccessReader` с читателем,
    считающим байты, и опциями §4.1, затем передаётся фабрике (§4.2) — детерминированно, без замеров
    времени;
  - распаковка записи читает только её локальный заголовок и сжатые данные.
- Большие архивы на диске читаются с произвольным доступом (§4.1): память пропорциональна размеру
  центрального каталога и открытой записи, а не архива. Архивы не на `file:` читаются в память
  целиком (лимит — `zipDocument.maxInMemoryArchiveSize`, §8).
- Лимит на открытие одной записи (`zipDocument.maxEntrySize`, по умолчанию 50 МБ) — сверх него ошибка.

### Заложить возможность, но не требуется реализация в v1
- Список в webview — виртуализированный (рендер только видимых строк).

## 7. Безопасность

- Ничего не распаковывается на диск, поэтому zip-slip неприменим;
- Все защиты при чтении записи — в `ZipArchive.read()` (§4.2), через него проходит любое чтение:
  - zip-бомба: заявленный размер сверяется с лимитом до распаковки, фактически распакованное не может
    превысить заявленное (`validateEntrySizes`);
  - повреждённые данные: сверка CRC-32;
  - шифрование и неподдерживаемые методы: отказ до чтения данных.
- Битые архивы: понятное сообщение об ошибке в webview вместо падения (`Corrupt`, §4.2).

## 9. Решения и открытые вопросы

2. ZipReader — библиотека `yauzl`. Обоснование:
   - сложность ZIP не в основном разборе, а в краевых случаях (ZIP64, CP437 / 0x7075, сигнатура EOCD
     внутри комментария, данные перед архивом, data descriptor, проверка смещений и размеров) —
     в `yauzl` они отлажены на реальных архивах;
   - оба нужных способа открытия есть из коробки: `open` — произвольный доступ к файлу на диске,
     `fromBuffer` — архивы не на `file:`; своя прослойка над источником байт не нужна;
   - требования §3 и §4.2 к составу выполняет сам: распаковывает ровно stored и deflate, декодирует
     имена по §4.2, некорректные имена отвергает (`validateFileName`);
   - зависимости маленькие (`buffer-crc32`, `pend`), типы — `@types/yauzl`.

   Отклонены: `adm-zip`, `jszip`, `fflate` — архив целиком в памяти; `node-stream-zip` — только
   файлы на диске, архивы не на `file:` не открыть; `unzipper` — ориентирован на поточную распаковку;
   свой парсер — оправдан лишь при нуждах сверх `yauzl` (например, восстановление битых архивов),
   которых в v1 нет.
3. VS Code for the Web — не поддерживается, только десктоп (§3).
4. Форматы на основе ZIP (`.jar`, `.vsix`, `.docx`…) — приоритет `option`, `*.zip` — `default`
   (список — §4.5). Обоснование: для таких файлов у пользователя может быть своё расширение
   (Java-инструменты для `.jar`, просмотрщик `.docx`/`.epub`), и `default` перехватил бы их открытие
   из Explorer. Для `.zip` другого естественного редактора нет.
5. Имя записи → путь URI — проверка `yauzl`, нормализация, один путь на запись (правила — §4.2).
   Обоснование:
   - имя в ZIP — произвольная строка: `..`, ведущий `/`, буква диска, `a//b`, `./a`, дубликаты
     (спецификация ZIP их не запрещает), запись `a` рядом с `a/b`;
   - имя с `..`, ведущим `/` или `X:/` — некорректное, архив не открывается (§3, §4.2). Изучение
     подозрительных архивов — не цель, а показывать такие записи значило бы переписывать их имена
     в пути;
   - `a//b` и `./a` проверку проходят, но путём URI в таком виде быть не могут: `Uri.joinPath` и
     части VS Code их нормализуют, и запись оказалась бы доступна под двумя путями или ни под
     одним. Нормализация обычные имена не меняет;
   - при конфликте путь получает каталог, иначе пропали бы все записи под ним; из дубликатов —
     первая по порядку в центральном каталоге. Проигравшие записи, как и зашифрованные (§3),
     видны в списке, но не открываются.
6. `mtime` в `FileStat` записи — `mtime` архива (правило — §4.4). Обоснование:
   - по документации `FileSystemProvider.onDidChangeFile` после события `mtime` в `stat` должен
     вырасти, иначе VS Code может не перечитать открытый редактор;
   - дата записи в ZIP этого не гарантирует: инструменты воспроизводимой сборки ставят всем записям
     одну фиксированную дату (1980-01-01 или `SOURCE_DATE_EPOCH`), и после пересборки архива дата
     изменённой записи остаётся прежней — вкладка не обновилась бы, сценарий 3 сломан;
   - `mtime` архива растёт при любой его перезаписи. Цена — после изменения архива перечитываются
     все его открытые вкладки, а не только изменившиеся; для архива только для чтения это приемлемо.

7. Лимиты размера — жёсткие, без подтверждения: запись больше `maxEntrySize` и архив не на `file:`
   больше `maxInMemoryArchiveSize` не открываются, пользователь видит ошибку с размером и именем
   настройки (правила — §4.4, §4.5). Обоснование:
   - `readFile` вызывается и в обход списка: восстановление вкладок после перезагрузки, недавние
     файлы, другие расширения через `workspace.fs`, `ZipReader` для архива с `zip:`-URI (связь 7 → 3). Лимит,
     который проверяет только ZipEditorProvider, обходится, и запись с заявленными 4 ГБ выделится в
     памяти extension host;
   - подтверждение в `readFile` (модальный диалог) покрыло бы все пути, но всплывало бы и от
     фонового чтения другим расширением;
   - нужен больший лимит — пользователь меняет настройку.

8. Время жизни `ZipArchive` у провайдеров (правила — §4.4, §4.5). Обоснование:
   - ZipEditorProvider — время жизни документа: самый простой вариант, владелец и момент закрытия
     очевидны. В v1 открытый архив нужен редактору только ради `index`, поэтому дескриптор файла
     (или буфер архива не на `file:`) держится дольше необходимого — это осознанная цена простоты;
     заодно архив уже открыт для будущего «Сохранить как…». Отклонено: закрывать сразу после
     построения списка и хранить только `index`;
   - ZipFileSystemProvider — пока архив наблюдается. Это совпадает со временем, когда из него открыты
     вкладки: VS Code вызывает `watch` для каждой открытой вкладки и `dispose` при её закрытии. Без
     наблюдения — на время вызова: такие вызовы редки, и держать архив некому сказать, когда хватит.

## 10. Критерии готовности v1

- Сценарии 1–3 из §2 работают на Linux/macOS/Windows и в Remote-SSH.
- Юнит-тесты `ZipReader` + `ZipArchive` (§4.1, §4.2): stored, deflate, ZIP64, UTF-8/CP437 имена,
  Unicode Path (0x7075), пустой архив, битый архив, `Corrupt` при некорректном имени (`..`,
  ведущий `/`, `X:/`), объём чтения при открытии (§6); одинаковый
  `ZipArchive` для архива с диска и из буфера; повторный `close()`; отказы `Encrypted`,
  `UnsupportedMethod`, `TooLarge` до чтения данных; `readable` совпадает с тем, примет ли запись
  `openReadStream` `yauzl` (шифрование × метод); `Corrupt` при завышенном и
  заниженном `uncompressedSize` и при неверном CRC-32.
- Юнит-тесты построения путей (§4.2): нормализация (`a//b`, `./a`),
  неявные каталоги, дубликаты, конфликт файл/каталог.
- Юнит-тесты формата `zip:`-URI (§4.3): построение и разбор туда-обратно, в т. ч. `zip:`-URI архива и
  пути с символами, требующими кодирования (`%`, `?`, `#`, пробел).
- Интеграционный тест: открытие архива кастомным редактором и файла через схему `zip`.
