URI записи ZIP-архива

  zip-document://v1/<метка>?pkg=<URI архива>&entry=<base64url байт имени>[&index=<n>]

Как читать. Раздел 1 — цели формата (Т1–Т8) и термины; термины в разделах 2–3 понимаются в этом
смысле. Нормативны разделы 2–3: по ним две независимые реализации обязаны получить один и тот же
URI и одинаково решить, принимать ли чужой. Раздел 4 — что из контракта следует: как достигнуты
цели и где их пределы. Разделы 5–8 и приложение не нормативны: почему так (5, ссылки вида
[Р3]), чем подтверждено (6), как сделано сейчас (7), что отклонено и почему (8, ссылки вида [О2]),
что говорит об именах APPNOTE (приложение). Правило, без которого нет совместимости, должно
быть в разделе 3; если реализация расходится с разделом 3, исправляется реализация.

Реализация для сверки — `probes/uri-format/uri.js`. Она показывает контракт в коде и на ней
проверяются его следствия (раздел 6), но контракт она не определяет: поведение кода, которого
нет в разделе 3, правилом формата не является.


# 1. Назначение

URI нужен, чтобы VS Code открывал запись ZIP-архива как файл: вкладка, языковой режим, иконка,
`watch`, `workspace.fs`. Строит его редактор архива (переход по записи), разбирает провайдер
файловой системы схемы `zip-document`; остальные — VS Code, другие расширения — передают его как
есть.

Не решает: иерархию каталогов — `readDirectory`, архив как папка рабочей области [Р12];
относительные ссылки между записями [Р7]; отождествление одного архива под разными URI [Р4].

Цели формата (Т1–Т8). Они определяют, какие свойства должен обеспечить контракт; сами правила
заданы в разделе 3, как цели достигнуты и где их пределы — в разделе 4.

Т1. Достижимость: у каждой записи центрального каталога есть URI — при любом имени, в том числе
    пустом, с `..`, ведущим `/`, недекодируемыми байтами, и при дубликатах имён.
Т2. Единственность: у записи ровно один URI, и из URI, дошедших до провайдера, он принимает
    только его. Для VS Code у записи поэтому один ресурс: один TextDocument, одна вкладка, один
    `watch`.
Т3. Устойчивость к VS Code: URI доходит до провайдера без изменений любым путём — `workspace.fs`,
    `openTextDocument`, `vscode.open`, и через строку `toString()` → `Uri.parse`.
Т4. Стабильность: URI не зависит от данных записи, её метаданных и других записей, кроме
    одноимённых. После пересборки архива и изменения данных URI тот же, если сохранились имя и
    порядок среди одноимённых; той же записью между версиями архива считается именно это (раздел 2).
Т5. Вложенность: архивом может быть запись другого архива.
Т6. Проверка без чтения архива: каноничен ли URI, решается по одному URI.
Т7. Удобство: заголовок вкладки, языковой режим и иконка — по имени записи; имя читается как
    есть, без процентного кодирования.
Т8. Различимость. Строго: у разных записей одного архива разный path, и VS Code различает их
    вкладки. На глаз: явно показаны строение имени (сегменты `""`, `.`, `..`, завершающий `/`),
    номер дубликата, байты вне UTF-8, управляющие, невидимые и пробельные символы — кроме тех,
    без которых текст отображается неправильно (ZWJ, ZWNJ, селекторы вариантов, 3.2). Что на глаз
    не различить и почему это принято — раздел 4.

Термины:
- запись — запись центрального каталога архива;
- имя — байты поля имени записи в центральном каталоге (не Unicode Path Extra Field 0x7075, не
  имя из локального заголовка) [Р2];
- одноимённые записи, дубликаты — записи с побайтно равными именами;
- index — номер записи среди одноимённых в порядке центрального каталога, с 0 [Р3];
- запись каталога — запись, имя которой оканчивается на `/`;
- архив — ресурс VS Code с ZIP-архивом, задан своим URI любой схемы, в том числе `zip-document`;
- метка — path URI записи;
- генератор — код, который строит URI записи; провайдер — `FileSystemProvider` схемы
  `zip-document`.


# 2. Модель адресации

Запись задаётся тройкой (URI архива, имя, index). Больше формат о записи ничего не знает: данные,
даты, флаги, extra-поля, смещения, соседние записи в адрес не входят.

index — позиция среди одноимённых записей, а не идентичность содержимого. Если в пересобранном
архиве одноимённые записи переставлены, их URI остаются прежними, а под ними — другие данные.
Одноимённые записи ничем, кроме порядка, не различаются, и формат не пытается узнавать их между
версиями архива [Р3].

Компоненты URI делят обязанности:
- query — адрес: URI архива, имя, index [Р1];
- path — метка: однозначно получается из (имя, index) и обратно; показывает запись человеку и
  VS Code, но адресом не служит [Р1, Р7];
- authority — версия формата [Р9];
- scheme — владелец формата [Р10];
- fragment — не используется [Р8].

У каждой тройки ровно один URI — канонический (3.4). Любой другой URI схемы `zip-document` — не
URI записи.


# 3. Контракт

## 3.1 Компоненты

Компоненты — поля `vscode.Uri`.

scheme     `zip-document`. [Р10]
authority  `v1`. [Р9]
path       метка, 3.2. [Р1, Р7]
query      адрес, 3.3. [Р1, Р3–Р6]
fragment   пустой. [Р8]


## 3.2 Метка (path)

Экранирование — `⟦…⟧` (U+27E6, U+27E7). Формы:
  `⟦HH⟧`              байт, не входящий в корректную последовательность UTF-8; HH — две заглавные
                      шестнадцатеричные цифры;
  `⟦U+XXXX⟧`          символ, который не показывается как есть; XXXX — заглавные
                      шестнадцатеричные цифры, не меньше четырёх, без лишних ведущих нулей;
  `⟦⟧` `⟦.⟧` `⟦..⟧`   сегмент, равный строго `""`, `.`, `..`;
  `⟦#N⟧`              номер дубликата, N = index ≥ 1, десятичное без ведущих нулей.

Метка из (имя, index):
1. Байты имени читаются слева направо. Корректная последовательность UTF-8 (RFC 3629: без
   избыточных форм, без суррогатов, не выше U+10FFFF) — её символ; любой другой байт — `⟦HH⟧`,
   и чтение продолжается со следующего байта.
2. Символ из списка ниже — `⟦U+XXXX⟧`, остальные — как есть.
3. Один завершающий `/` (признак записи каталога) снимается и запоминается.
4. Строка делится по `/`. Сегмент, равный строго `""`, `.`, `..`, заменяется на `⟦⟧`, `⟦.⟧`,
   `⟦..⟧`. Ни один сегмент не отбрасывается и не разрешается.
5. Если был снят завершающий `/` — к последнему сегменту дописывается `⟦U+002F⟧`.
6. index ≥ 1 — перед последним сегментом вставляется сегмент `⟦#index⟧`.
7. path = `/` + сегменты через `/`.
8. path начинается с `/X:`, где X — заглавная латинская буква A–Z, — X заменяется на
   `⟦U+00XX⟧`.

Список символов шага 2 — замороженный. Нормативна таблица ниже; получена она так: по Unicode 17.0
объединение категорий Cc, Cf, Zl, Zp, Zs и свойств Default_Ignorable_Code_Point,
Noncharacter_Code_Point, из него исключены U+0020, ZWJ U+200D, ZWNJ U+200C и селекторы
вариантов (FE00–FE0F, E0100–E01EF, монгольские 180B–180D и 180F), добавлен сам `⟦` U+27E6:
  0000–001F  007F–00A0  00AD  034F  0600–0605  061C  06DD  070F  0890–0891  08E2
  115F–1160  1680  17B4–17B5  180E  2000–200B  200E–200F  2028–202F  205F–206F
  27E6  3000  3164  FDD0–FDEF  FEFF  FFA0  FFF0–FFFB  FFFE–FFFF  110BD  110CD
  13430–1343F  1BCA0–1BCA3  1D173–1D17A  E0000–E00FF  E01F0–E0FFF
  и nFFFE–nFFFF в плоскостях 1–16.
Исключённые символы остаются как есть (Р7). Никакой другой обработки нет, в том числе
нормализации Unicode: регистр, NFC/NFD, пробел U+0020, `\`, `%`, `?`, `#`, `⟧` остаются как есть.

Свойства метки — следуют из шагов, на них опираются гарантии раздела 4:
- начинается с `/`; нет сегментов `""`, `.`, `..`; не оканчивается на `/`; не начинается с
  `/X:` (X — A–Z);
- вне экранирований нет ни одного символа списка шага 2;
- по метке однозначно восстанавливаются имя и index (3.5).


## 3.3 Адрес (query)

query — ровно эта строка, параметры в этом порядке, разделитель `&`:

  pkg=<P>&entry=<E>            для index = 0
  pkg=<P>&entry=<E>&index=<N>  для index ≥ 1

P — `toString()` URI архива [Р4]. P не содержит `&` и `=` (их кодирует `toString()`) и
    совпадает со своим `toString(Uri.parse(P))`.
E — имя, base64url (RFC 4648 §5) без паддинга. Пустое имя — пустая строка (`entry=`). [Р2, Р6]
N — index, десятичное без ведущих нулей, от 1 до 2^53 − 1; при index = 0 параметр не пишется.
    Для index больше 2^53 − 1 URI нет. [Р3]


## 3.4 Каноническая форма; генератор и провайдер

URI каноничен, если он покомпонентно — scheme, authority, path, query, fragment, строгим
равенством строк — равен URI, построенному по 3.1–3.3 из какой-либо тройки (архив, имя, index).
Тройка, если она есть, извлекается из query однозначно: query делится по `&` на 2 или 3 части с
префиксами `pkg=`, `entry=`, `index=` по порядку; значения берутся как есть, без процентного
декодирования и без правил форм (`+` — не пробел) [Р5].

Каноничность — свойство URI, который получил провайдер. Что VS Code делает с URI до провайдера
(приводит authority к нижнему регистру, отбрасывает fragment, нормализует path), контракт не
определяет и провайдер увидеть не может; что из этого следует — раздел 4, Т2.

Генератор строит только канонические URI. P — URI, под которым VS Code открыл архив [Р4].

Провайдер:
- неканонический URI не обслуживает: на любой вызов (`stat`, `readFile`, `watch`, …)
  отвечает отказом и записи не читает; каким именно отказом — не часть формата [Р11];
- не исправляет URI на канонический [Р11];
- по каноническому URI читает запись архива P с этим именем и этим index;
- регистрирует схему с `isCaseSensitive: true` — VS Code сравнивает path с учётом регистра, как
  и определение каноничности; query VS Code сравнивает с учётом регистра всегда — и с
  `isReadonly: true`.

Из определения следует, что не каноничны, например:
- authority `V1`, `v2`, пустая; непустой fragment;
- path, не равный метке: `/B` при `entry=QQ` (имя `A`), `/./A`, метка по другой версии правил;
- параметры в другом порядке, лишние, повторённые, без `entry`;
- E не в канонической форме: `QR`, `QQ==`, `Q Q`, `QQ!` (все они при нестрогом декодировании
  дают байт `A`), `+/8` (base64, не base64url);
- `index=0`, `index=`, `index=01`, `index=1e1`, `index=-1`, больше 2^53 − 1;
- P, не равный своему `toString()`: `file:///C:/x.zip` вместо `file:///c%3A/x.zip`; пустой.


## 3.5 Обратимость

По каноническому URI восстанавливается тройка: архив — `Uri.parse(P)`, имя — декодирование E,
index — N или 0.

По метке, без query, восстанавливаются имя и index: символ вне экранирования — его байты UTF-8;
`⟦HH⟧` — байт; `⟦U+XXXX⟧` — байты UTF-8 символа; `⟦⟧`, `⟦.⟧`, `⟦..⟧` — сегмент `""`, `.`,
`..`; `⟦U+002F⟧` в конце — завершающий `/`; сегмент `⟦#N⟧` — index, сам он в имя не входит;
`/` вне экранирований — разделитель. Однозначно, потому что каждый `⟦` в метке открывает
экранирование: настоящий `⟦` из имени экранирован.


## 3.6 Строковая форма

Строка URI — `uri.toString()`, обратно — `Uri.parse(s)`. `toString()` процентно кодирует в
компонентах всё, кроме `A–Z a–z 0–9 - . _ ~` (и `/` в path): разделители формата в query
становятся `%3D` и `%26`, `%` из P — `%25`, символы метки вне ASCII — UTF-8 в `%XX`; E
остаётся как есть. Это кодирование VS Code, не формата: на уровне полей `Uri`
компоненты такие, как в 3.1–3.3.

`toString(true)` — только для показа: он не кодирует `&` и `=`, и `Uri.parse` от него для
архива с `%` в URI даёт другой query.


## 3.7 Примеры

Архив `file:///home/u/release.zip`.

    path   /src/main.ts
    query  pkg=file:///home/u/release.zip&entry=c3JjL21haW4udHM
    строка zip-document://v1/src/main.ts?pkg%3Dfile%3A%2F%2F%2Fhome%2Fu%2Frelease.zip%26entry%3Dc3JjL21haW4udHM

  src/main.ts, второй дубликат
    path   /src/⟦#1⟧/main.ts
    query  pkg=file:///home/u/release.zip&entry=c3JjL21haW4udHM&index=1

  пустое имя
    path   /⟦⟧
    query  pkg=file:///home/u/release.zip&entry=

  ./a//../b.txt
    path   /⟦.⟧/a/⟦⟧/⟦..⟧/b.txt

    строка zip-document://v1/%E2%9F%A6.%E2%9F%A7/a/%E2%9F%A6%E2%9F%A7/%E2%9F%A6..%E2%9F%A7/b.txt?pkg%3Dfile%3A%2F%2F%2Fhome%2Fu%2Frelease.zip%26entry%3DLi9hLy8uLi9iLnR4dA

    path   /a/b⟦U+002F⟧

    path   /d/⟦84⟧.txt

  META-INF/MANIFEST.MF внутри lib/x.jar

# 4. Гарантии и пределы

Часть гарантий следует из контракта сама по себе, часть — из контракта и поведения VS Code. Где
нужно второе, это сказано; само поведение и версии, на которых оно проверено, — раздел 6.

Т1, достижимость. Любые байты имени и любой index до 2^53 − 1 дают URI (3.2–3.3): шаг 1 метки
не отказывает ни на каких байтах, E кодирует любые байты.

Т2, единственность. Тройка ↔ канонический URI — биекция: URI строится из тройки однозначно, а
тройка восстанавливается из URI (3.5). Провайдер принимает только канонический URI (3.4).
Это гарантия на границе провайдера: он видит URI таким, каким его передал VS Code. Разные
строки, отданные в API VS Code, VS Code может свести к одной до вызова провайдера: `V1` и `v1`
в `openTextDocument`, URI с fragment и без в `vscode.open`. Запись от этого не раздваивается:
сведённые строки VS Code и сам считает одним ресурсом — один TextDocument, одна вкладка. Строки,
которые VS Code различает как ресурсы, доходят до провайдера разными, и из них принимается только
каноническая. Что разные ресурсы VS Code не доводят до провайдера одной строкой, — свойство
VS Code, а не контракта; проверено на 1.145.2 (раздел 6). Если это изменится, у записи появится
второй документ, и провайдер этого не увидит.

Т3, устойчивость к VS Code. Контракт даёт синтаксические свойства: у метки нет сегментов `""`,
`.`, `..`, завершающего `/` и `/X:` в начале (3.2); query и fragment заданы точно. С поведением
VS Code — он меняет в path только такие сегменты и регистр буквы в `/X:`, query не меняет,
fragment отбрасывает — это значит, что URI доходит до провайдера как есть. Проверено на VS Code
1.145.2 (раздел 6); если VS Code начнёт менять что-то ещё, гарантия потеряна, а провайдер будет
отвечать отказом на изменённые URI — запись не откроется, но и чужая не прочитается.

Т4, стабильность. URI зависит только от тройки (раздел 2). После пересборки архива URI меняется,
только если до записи добавлены, удалены или переставлены одноимённые записи. Это предел:
одноимённые записи различаются только порядком, а URI отвечает за позицию, не за содержимое.
Метка не зависит от версии Unicode среды — список шага 2 заморожен.

Т5, вложенность. P — URI любой схемы, в том числе `zip-document` (3.3).

Т6, проверка без архива. Каноничность определена через построение URI из тройки, которую даёт
сам URI (3.4); архив нужен только для поиска записи.

Т7, удобство. Имя в метке как есть, кроме экранирований; заголовок вкладки, языковой режим и
иконка VS Code берёт из последнего сегмента path. В подписях VS Code показывает path без
процентного кодирования и без нормализации Unicode (проверено, раздел 6).

Т8, различимость.
- Строго: у разных записей одного архива разный path — следует из обратимости метки (3.5).
  Что при разном path VS Code держит разные вкладки, — его поведение при `isCaseSensitive: true`
  (3.4); проверено, раздел 6.
- На глаз — всё, что перечислено в Т8, показано экранированием или отдельным сегментом.
- Пределы — path разный, но выглядит одинаково:
  · канонически эквивалентные формы: `café` в NFC и NFD;
  · похожие буквы разных письменностей: латинская `caca` и кириллическая `саса`, `0` и `O`;
  · различия только в ZWJ, ZWNJ, селекторах вариантов;
  · символы, которые станут невидимыми или форматными в Unicode новее 17.0 — список заморожен,
    расширить его можно только новой версией формата [Р9].
  Предел принят сознательно: это нормальные имена, и путать такие имена люди привыкли везде, не
  только в архивах; цена полной различимости — нечитаемые метки обычных имён [О13].

Прочие пределы:
- index больше 2^53 − 1 URI не получает (3.3); архива со столькими одноимёнными записями быть не
  может на практике [Р3].
- Один архив под разными строками URI (регистр на нечувствительной ФС, символьные ссылки,
  локальный путь и `vscode-remote:`) — разные P, разные URI записей [Р4].
- Имена в однобайтовых кодировках без бита 11 (CP437, CP866, Shift-JIS) — в метке байтами
  (`⟦84⟧`): ASCII читается, остальное нет [Р7]. Читаемое имя по флагам может показать список
  записей в редакторе архива.
- Относительные ссылки между записями (картинка из Markdown-файла архива) не работают —
  провайдер отказывает [Р7].
- Длина. Метка ≈ длина имени плюс 4–10 символов на каждое экранирование; E ≈ 4/3 байтов имени.
  Каждый уровень вложенности включает строку внешнего URI целиком и ещё раз экранирует её `%`:
  для имени `inner/archive.zip` длина строки на глубинах 1–5 — 114, 220, 344, 486, 646
  символов. Предела длины в VS Code не нашли, но и не искали.
- `⟦⟧` должны быть в шрифте интерфейса; проверено только на Linux (раздел 6).


# 5. Обоснования

Почему правила раздела 3 такие — доводы за принятое. Наблюдения, на которые доводы опираются, —
раздел 6; отклонённые варианты и прежние правила — раздел 8 (ссылки вида [О2]).

## 5.1 Модель адресации

Р1. Адрес — в query, path — только метка.
    Path непригоден как адрес: VS Code и `vscode-uri` меняют его по дороге, и это не отключить
    (6.1):
    - `openTextDocument` и `vscode.open` проводят URI через `UriIdentityService.asCanonicalUri`
      → `normalizePath`: сегменты `""`, `.`, `..` схлопываются, `..` упирается в корень. Записи
      `a//b` и `a/b` получили бы один URI, `a/../b` — чужой, `..` — `/`;
    - `toString()` переводит в нижний регистр заглавную букву в `/X:` в начале path, после
      `Uri.parse` path уже другой;
    - пустой path VS Code не открывает, одиночный суррогат — `URI malformed`.
    Кроме того, `Uri.path` — строка, не байты: байт 0xFF и текст `%FF` не различить, а
    недекодируемое имя не выразить вовсе; дубликаты имён path не различает в принципе.
    Query VS Code не меняет ни одним путём и сравнивает с учётом регистра.
    Path — не адрес, но и не произвольная подпись: адрес в пределах архива из него
    восстанавливается (3.5), только читать его оттуда незачем — он в query. [О1, О2]

Р2. Запись идентифицируется байтами имени из центрального каталога.
    - Декодированная строка не годится: разные байты дают одну строку (недекодируемые байты →
      U+FFFD; CP437 и UTF-8 у разных записей), и запись стала бы недостижимой.
    - Unicode Path Extra Field (0x7075) необязателен, может не совпадать с именем или
      отсутствовать у части записей; имя в локальном заголовке может отличаться от каталога.
      Центральный каталог — то, по чему архив читают читатели с произвольным доступом; поточные,
      идущие по локальным заголовкам, — не наш случай.
    - Байты — единственное, что у записи есть всегда, включая пустое имя.

Р3. Дубликаты различает index среди записей с тем же именем.
    - Только порядок отличает записи с одинаковыми байтами имени (APPNOTE дубликаты не
      запрещает; `probes/duplicate-names`).
    - Номер считается среди одноимённых: он меняется, только если до записи добавлены, удалены
      или переставлены одноимённые записи (Т4), и не зависит от содержимого. При изменении
      записи URI открытой вкладки остаётся тем же: её `watch` получает `Changed`, а не
      `Deleted`, и вкладка обновляется. Отсюда и предел: позиция, а не содержимое (раздел 2).
      [О3]
    - При 0 не пишется: дубликаты редки, почти все URI короче и читаемее. Цена — правило «0 не
      пишется», без него `index=0` и отсутствие index были бы двумя URI одной записи (Т2).
    - Номер виден и в path — сегментом `⟦#N⟧` (Р7), иначе вкладки дубликатов не различить (Т8).
    - Не больше 2^53 − 1: это наибольшее целое, которое число с плавающей точкой (`Number` в
      JavaScript) хранит точно; без границы реализация на таких числах и реализация на длинных
      целых по-разному решали бы, каноничен ли `index=9007199254740993`. Предел недостижим:
      одни заголовки центрального каталога стольких записей заняли бы больше 400 ПБ.

Р4. Архив — его `toString()`.
    - Строка URI — единственная форма, которая есть у любого URI любой схемы, включая
      `zip-document` (Т5).
    - `toString()` кодирует `&` и `=` во всех компонентах (раздел 6), поэтому P никогда их не
      содержит и деление query по `&` однозначно без своего экранирования. `toString(true)` не
      кодирует — не годится.
    - Каноничность P — через `toString(parse(P)) = P`: `toString` на своих строках тождествен, а
      разные строки одного URI архива (`C:` и `c%3A`) отвергаются.
    - P берётся у VS Code — URI документа редактора архива; его VS Code уже канонизировал.
      Отождествлять один архив под разными URI формат не берётся: для этого пришлось бы
      разбирать URI архива, а схема архива может быть любой (раздел 4).

## 5.2 Адрес: query

Р5. Свой разбор query: деление по `&` и префиксы.
    При фиксированном порядке и известных именах параметров больше ничего не нужно. Значения не
    декодируются: P должна остаться той строкой, что дал `toString()`, и `+` в ней — `+`. [О4]

Р6. Байты имени — base64url без паддинга.
    - Нужна своя кодировка байт: `Uri.query` — строка (Р1).
    - Алфавит base64url `A–Z a–z 0–9 - _` целиком из незарезервированных символов: `toString()`
      оставляет E как есть, в строке URI он тот же, что в `Uri.query`, — один слой экранирования.
      Base64url — стандартная кодировка, правило одно. Паддинг избыточен: длина известна. [О5]
    - Каноничность E — только сравнением с перекодированным, а не «успешно декодировалось»:
      распространённые декодеры base64url нестрогие (раздел 7).

## 5.3 Метка: path

Р7. Метка: полный путь; обратимая и видимая; строго проверяется; вычисляется из одних байтов.
    Метка — то, что видят VS Code и человек: заголовок, описание вкладки, крошки, подсказка,
    языковой режим, иконка. Она показывает запись в архиве, а не то, во что превратит её путь
    разрешение или распаковка.

    - Полный путь, а не базовое имя: одноимённые вкладки (`a/README.md` и `b/README.md`)
      VS Code подписывает каталогом из path (`/a`, `/b`), хлебные крошки — сегменты path
      (раздел 6); с базовым именем различать было бы нечем. Языковой режим и иконка — по
      последнему сегменту, как у базового имени. Цена — длиннее URI.

    - Обратимость (Т8). Метка — функция (имя, index), и по метке они восстанавливаются (3.5).
      Из обратимости следует, что две записи одного архива одного path не получат. Отсюда
      условия для каждого шага:
      · одно экранирование `⟦…⟧` на всё, и сам `⟦` экранируется: тогда каждый `⟦` в метке
        открывает экранирование, и метка читается однозначно; `⟧` вне экранирования ничего не
        значит и остаётся как есть;
      · никаких «похожих» замен: значок `␀` вместо NUL совпал бы с настоящим `␀` в имени,
        U+FFFD вместо символов направления — с настоящим `�` и друг с другом;
      · никакого угадывания кодировки (ниже);
      · ничего не отбрасывать: сегменты `""`, `.`, `..`, завершающий `/`, номер дубликата.

    - Скобки `⟦⟧` (U+27E6, U+27E7). От выбора пары зависит только читаемость меток, не
      верность формата: однозначность даёт экранирование самого `⟦`, при любой паре. От пары
      нужно: не подделать ASCII-символами (иначе имя `<84>.txt` выглядело бы как экранированный
      байт); не путать с `[` (шрифт интерфейса рисует `⟦⟧` двойными, раздел 6); редко
      встречаться в именах. Частоту не измеряли: белые квадратные скобки — математический знак.
      Если `⟦` в имени есть, экранируется только он (`⟦U+27E6⟧`; `⟧` остаётся как есть), и
      такая метка заметна — для необычного имени это скорее сигнал, чем шум. [О6]

    - Содержимое экранирования — то, что заменено, а не описание: `⟦84⟧` — байт 0x84,
      `⟦U+202E⟧` — символ U+202E, `⟦..⟧` — сегмент `..`. Код символа понятен без таблиц,
      есть у любого символа и однозначен. [О7]

    - Декодирование — UTF-8 с экранированием байтов, без запасной кодировки.
      · Любая запасная кодировка нарушает обратимость: байты `C3 A4` (UTF-8) и `84` (CP437)
        дали бы одно `ä`, две записи — одну метку. `⟦84⟧` показывает, что в имени байт,
        который не UTF-8, и какой именно. [О8]
      · Только из байтов, не из флага UTF-8 (бит 11) и 0x7075, как декодируют имена библиотеки
        чтения ZIP: метка зависела бы от метаданных — ломается Т4 при пересборке другим
        инструментом и Т6 (нужен архив), а разные байты снова дали бы один текст.
      · Цена: имена в однобайтовых кодировках без бита 11 читаются хуже — ASCII как есть,
        остальное байтами. Правильно их без угадывания не декодировать всё равно.
      · Байты разбираются по одному: некорректный байт — `⟦HH⟧`, дальше разбор со следующего.
        Так каждый байт либо в символе, либо в своём экранировании, и обратное однозначно.

    - Какие символы экранируются (шаг 2). Те, что не видны или действуют, — по ним два имени
      различаются незаметно или имя выглядит не тем, что оно есть (Т8):
      · управляющие C0, DEL, C1 и разделители строк (U+2028, U+2029): перевод строки обрывает
        крошку, NUL не виден и пропадает из подсказки (раздел 6);
      · символы направления (встраивание, переопределение, изоляция; LRM, RLM, ALM):
        `invoice<U+202E>txt.exe` без экранирования выглядит как `invoiceexe.txt`, хотя иконка
        и языковой режим — от `.exe`; архив — недоверенные данные;
      · невидимые и игнорируемые при отрисовке (ZWSP, BOM, мягкий перенос, word joiner,
        теги, заполнители хангыля и др.): `a<ZWSP>b` выглядит как `ab`;
      · пробелы, кроме U+0020 (NBSP, U+2000–U+200A, U+3000 и др.): `a<NBSP>b` выглядит как
        `a b`;
      · несимволы (U+FFFE и др.) — не предназначены для текста;
      · сам `⟦`.
      Как есть — ZWJ, ZWNJ и селекторы вариантов: без них неправильно рисуются эмодзи (семья —
      несколько эмодзи через ZWJ; сердце с U+FE0F), персидский и индийские письменности. Их
      различие невидимо — раздел 4. [О13]
      · Список заморожен диапазонами, а не задан свойствами Unicode: свойства меняются от
        версии к версии, и с обновлением среды менялись бы метки, а с ними URI сохранённых
        вкладок (Т4). Получен из свойств Unicode 17.0; совпадение проверено (раздел 6).

    - Сегменты `""`, `.`, `..` — `⟦⟧`, `⟦.⟧`, `⟦..⟧`, ничего не отбрасывается.
      · `a/c/../b` — запись с `..` в имени, и человек должен это видеть: `/a/c/⟦..⟧/b`.
      · Как есть оставить нельзя: при открытии VS Code нормализует path (Р1) — схлопывает `""`
        и `.`, разрешает `..`; URI дошёл бы до провайдера изменённым и стал бы неканоническим.
        `⟦..⟧` — уже не `..`: VS Code его не трогает. [О9]

    - Завершающий `/` записи каталога — `⟦U+002F⟧` в конце последнего сегмента: `a/b/` →
      `/a/b⟦U+002F⟧`. Не убирать: каталог `a/b/` и файл `a/b` слились бы. Не оставлять `/`
      как есть: для VS Code это разделитель, заголовок вкладки `/a/b/` — `b`, как у файла
      `a/b` (`probes/uri-roundtrip`: path `/a//` → заголовок `a`). Экранирован сам символ, по
      общему правилу: в экранировании нет `/`, и VS Code по нему path не делит. [О10]

    - Номер дубликата — сегмент `⟦#N⟧` перед последним: `/src/⟦#1⟧/main.ts`. Заголовок
      вкладки, языковой режим и иконка — по имени файла, как у первой записи; номер VS Code
      показывает в описании вкладки (`/src/⟦#1⟧`) и в крошках (раздел 6); номер стоит рядом с
      именем, к которому относится. [О11]

    - Буква диска: `/X:` в начале — `/⟦U+00XX⟧:` (`C:/x` → `/⟦U+0043⟧:/x`). Заглавную
      `toString()` переводит в нижний регистр (Р1), URI изменился бы по дороге; экранирование
      сохраняет букву как есть, и `C:/x` и `c:/x` остаются разными записями. [О12]

    - Без нормализации Unicode (NFC, NFD, NFKC). VS Code показывает path символ в символ
      (раздел 6). Метка как есть — имя записи как есть. NFKC показал бы другое имя (`ﬁle` →
      `file`, `Ⅻ` → `XII`, `x²` → `x2`) и слил бы разные записи; NFC меняет даже одиночные
      символы (`Å` U+212B → U+00C5).

    - Проверяется строго (3.4), хотя адреса не несёт:
      · иначе `/x` и `/y` с одним query — два URI одной записи (Т2);
      · код, разрешающий относительную ссылку от открытого документа (`Uri.joinPath` от
        `dirname`), сохраняет query. Ссылка `./img.png` из `a/README.md` дала бы path
        `/a/img.png` с query README, и вместо картинки прочитался бы README. Со строгой
        проверкой — отказ;
      · URI по другой версии правил не будет понят по ошибке.

## 5.4 Fragment, authority, scheme

Р8. Fragment пуст.
    `openTextDocument` передаёт fragment провайдеру и заводит для URI с fragment отдельный
    TextDocument; провайдер такой URI отвергает, иначе у записи было бы два документа (Т2).
    `vscode.open` отбрасывает fragment до провайдера — открывается сама запись. Позицию в файле
    VS Code передаёт отдельно, fragment для неё не нужен. Строгая проверка ничего не стоит:
    канонический URI fragment не несёт. [О14]

Р9. Authority — версия формата `v1`.
    Вкладки и недавние файлы VS Code хранит и восстанавливает по URI, в том числе после
    обновления расширения. Если правила меняются (например, метки или счёт index), а параметры
    остаются те же, отличить старый URI от нового по форме нельзя — версия делает это явно:
    новая версия либо понимает `v1`, либо отказывает, но не читает чужую запись.
    Строчные: `openTextDocument` приводит authority к нижнему регистру, `V1` и `v1` для VS Code
    один ресурс. `v1` — коротко и читается как версия без пояснений.

Р10. Схема `zip-document`, не `zip`.
    Схему `zip` уже регистрирует расширение ZipFS (`arcanis.vscode-zipfs`, инструментарий Yarn
    PnP, URI вида `zip:/…/archive.zip/…`, активация `onFileSystem:zip`). Второй
    `registerFileSystemProvider` той же схемы бросает исключение (раздел 6): при установленном
    ZipFS одно из расширений не работало бы, а `zip:`-URI ZipFS могли бы прийти нашему
    провайдеру. `zip-document` — имя расширения: владелец очевиден, совпадение маловероятно.

## 5.5 Провайдер и границы формата

Р11. Всё неканоническое — отказ.
    Неканонический URI не строит никто, кроме чужого кода или старой версии. Для формата важно
    одно: по такому URI ничего не читается. Какой ошибкой отказать — решение провайдера и
    API VS Code, а не формата: никто из пользователей формата на конкретный код не опирается,
    исправить URI вызывающий всё равно не может, а набор ошибок VS Code может меняться. Исправлять
    URI на канонический нельзя: провайдер отвечает за тот URI, с которым вызван, и запись
    открылась бы под вторым URI (Т2). [О15]

Р12. Адресуются записи, не пути.
    - URI есть у каждой записи каталога, включая записи каталогов (`a/b/`, метка
      `/a/b⟦U+002F⟧`); что провайдер с ними делает (`stat` → `Directory`, `readFile` →
      ошибка), — дело провайдера, не формата.
    - Неявных каталогов (префиксов путей) в каталоге ZIP нет, поэтому нет и их URI; иерархию,
      `readDirectory` и открытие архива папкой рабочей области формат не даёт. Иерархия с
      дубликатами, `..` и конфликтом файла `a` с каталогом `a/` (`probes/path-conflicts`)
      потребовала бы правил разрешения, и часть записей снова стала бы недостижимой (Т1).
      Дерево показывает редактор архива.


# 6. Проверка

Свидетельства: что наблюдалось и где. Это не правила — правила в разделе 3.

## 6.1 Поведение VS Code, на котором стоят Т2, Т3, Т7, Р1, Р8, Р9

`probes/uri-roundtrip` (VS Code 1.145.2, Linux):
- `workspace.fs` доставляет URI без изменений; `openTextDocument` и `vscode.open` нормализуют
  path: `""`, `.`, `..` схлопываются, `..` упирается в корень (`/../../../a` → `/a`,
  `/a/..` → `/`). Без изменений доходят регистр, NFC/NFD, `.` и пробел в конце, `/` в конце,
  `\`, NUL, управляющие символы, текст `%XX`, U+FFFD;
- одиночный суррогат в path — `URI malformed`; пустой path не открывается; `/` открывается
  (пустой заголовок); заголовок вкладки для path `/a//` — `a`;
- authority: `openTextDocument` приводит к нижнему регистру до провайдера — разный регистр, один
  TextDocument; `vscode.open` и `workspace.fs` передают как есть;
- fragment: `vscode.open` отбрасывает до провайдера, вкладка одна; `openTextDocument` передаёт
  провайдеру и заводит отдельный TextDocument; `workspace.fs` передаёт;
- во всех случаях выше URI, для которых VS Code заводит разные TextDocument, доходят до
  провайдера разными строками (основа Т2, раздел 4);
- query не меняется ни одним путём и различается с учётом регистра;
- `watch` — один на URI, сколько бы редакторов его ни показывали; `unwatch` — после закрытия
  последнего.

`vscode-uri` 3.0.8 (код URI самого VS Code), `probes/uri-format/check.js`: `toString()`
переводит в нижний регистр заглавную букву в `/X:` в начале path; кодирует `&` и `=` во всех
компонентах; `toString(true)` их не кодирует и через `Uri.parse` не возвращается.

Код VS Code 1.145.2 (поиск по всем `out/**/*.js`): `normalize('NFKC'|'NFKD')` нет нигде.
`normalize('NFC')` — пути диска на macOS (`readdir`, события наблюдателя, диалоги,
`open-file`, аргументы CLI) и разбор ответов в чате; `normalize('NFD')` — только в
«убрать диакритику» для нечёткого поиска (копия строки для сравнения, показ не меняет).
URI других схем ни в одно из этих мест не попадают.

Повторная регистрация схемы — исключение «a provider for the scheme … is already registered»
(`probes/uri-format/vscode-probe.js`). ZipFS регистрирует `zip`: страница расширения
`arcanis.vscode-zipfs` в Marketplace и документация Yarn (`vscode-zipfs`).

# 7. Заметки по реализации

Как сделано в реализации для сверки (`probes/uri-format/uri.js`) и что учесть в своей. Может
устаревать независимо от контракта.

- Построение — `Uri.from({ scheme, authority, path, query, fragment })` из компонентов. Не
  склейкой строки (процентное кодирование пришлось бы делать вручную) и не `Uri.joinPath`
  (нормализует path).
- Каноничность — построить URI заново из извлечённой тройки и сравнить покомпонентно; отдельные
  проверки (регулярные выражения для E, N, P) не нужны и легко расходятся с генератором.
- P — `Uri.parse(P, true)`: строгий режим отвергает строку без схемы, а нестрогий подставил бы
  `file`; дальше расхождение всё равно поймает сравнение.
- E — `Buffer.from(E, 'base64url')`. Декодер Node нестрогий: `QQ`, `QR`, `QQ==`, `Q Q`, `QQ!`
  дают один байт `A`; канонической формой E делает только сравнение с перекодированным.
- N — `Number(N)` и проверка `Number.isSafeInteger`; `Number('')` = 0, `Number('1e1')` = 10 —
  такие формы отсекает сравнение.
- Query — без `URLSearchParams` (Р5).
- Шаг 1 метки — свой цикл по байтам (`utf8At` в `uri.js`): `TextDecoder` с заменой даёт U+FFFD
  на всю некорректную последовательность и теряет байты. Строгий `TextDecoder` (`fatal: true`)
  годится для проверки «имя — UTF-8 целиком» и сверен с циклом в `check.js`.
- Список шага 2 — таблица диапазонов, а не `\p{…}` в регулярном выражении: свойства в
  регулярных выражениях — из Unicode той версии, что в среде (Р7). `check.js` сверяет таблицу со
  свойствами среды, только если в ней Unicode 17.0.
- Исходники с экранируемыми символами — только escape-последовательности (`\u202e`), не сами
  символы: невидимые символы направления в исходном тексте — та же подмена, от которой метка
  защищает (`check.js` и пробы проверены на это).
- Отказ — `FileSystemError.FileNotFound(uri)`: для VS Code неканонический URI — ресурс, которого
  нет; так же отвечают пробы. Отдельные коды для разных нарушений не нужны.
- Регистрация — `registerFileSystemProvider('zip-document', provider, { isCaseSensitive: true,
  isReadonly: true })`; активация — `onFileSystem:zip-document` в `activationEvents`, иначе
  после перезагрузки окна VS Code восстановит вкладки раньше, чем схема зарегистрирована.
- Читаемое имя для списка записей в редакторе архива (по биту 11 и 0x7075) — дело редактора;
  с меткой оно может не совпадать (раздел 4).


# 8. Отклонённые варианты

Что рассматривалось и почему не принято, в том числе прежние правила этого формата. Нужно, чтобы
не возвращаться к тем же вариантам; в скобках — обоснование, к которому вариант относится.

О1 (Р1). Path как адрес: `zip:/<путь записи>?<URI архива>`. Проигрывает Т1 и Т2: VS Code меняет
    path по дороге, а байты вне UTF-8 и дубликаты path не выражает.

О2 (Р1). Гибрид: path — адрес для «чистых» имён, query — для остальных. Две формы, два разбора,
    и запись меняла бы форму URI при пересборке архива, когда рядом появляется дубликат.

О3 (Р3). Другие способы различать дубликаты:
    - общий номер записи в каталоге — менялся бы от добавления или удаления любой записи перед
      этой (Т4);
    - смещение записи — меняется при любой пересборке;
    - хэш данных — меняется с содержимым: URI открытой вкладки сменился бы, её `watch` получил бы
      `Deleted` вместо `Changed`, и вкладка не обновилась бы.

О4 (Р5). Разбор query по правилам HTML-форм (`URLSearchParams` и аналоги): декодировал бы `%XX`
    внутри P — строка URI архива исказилась бы — и превращал бы `+` в пробел.

О5 (Р6). Другие кодировки байтов имени:
    - base64 — `+`, `/`, `=` `toString()` кодирует, а `=` спорил бы с синтаксисом параметров;
      паддинг — по той же причине и потому, что избыточен;
    - своё процентное кодирование — ASCII-имена читались бы, но в строке URI `%` превращается в
      `%25` (`%25D0%25B0`): два слоя процентов — классический источник ошибок, а читаемое имя и
      так есть в метке.

О6 (Р7). Другие скобки экранирования: `<…>` и `[…]` — подделываются ASCII; `{…}`, `«…»` — часты в
    именах; `【…】` — часты в японских именах; U+FFFD — бывает в именах и уже значит «потеряно»,
    а не «показано иначе».

О7 (Р7). Значки вместо кода (`␊`, `␀`): красивее, но есть не для всех символов и совпадают с
    настоящими символами в имени.

О8 (Р7). Запасная кодировка CP437 для имён не в UTF-8 — прежнее правило: байты `C3 A4` (UTF-8) и
    `84` (CP437) давали одно `ä`, две записи — одну метку.

О9 (Р7). Сегменты `""`, `.`, `..`:
    - отбрасывать (одна из прежних редакций) — `a/b`, `a/./b`, `a//b`, `./a/b`, `/a/b` выглядели
      одинаково, `a/c/../b` — как настоящий `a/c/b` (раздел 6);
    - разрешать `..`, как POSIX и VS Code (`a/c/../b` → `/a/b`), — показывать место, которого в
      имени нет;
    - U+FFFD перед сегментом (`�..`) — совпадает с настоящим сегментом `�..`;
    - двойники вроде `‥` (U+2025) — странность не видна.
    Куда такие имена кладут распаковщики (`probes/dotdot-extract`, 6.5), — не довод: метка о
    записи, а не о распаковке.

О10 (Р7). Признак каталога `⟦/⟧` — первая версия: содержит `/`, VS Code делит по нему path, и
    заголовок вкладки каталога был `⟧` (раздел 6).

О11 (Р7). Номер дубликата в другом месте: в имени файла (`main⟦#1⟧.ts`) — ломает определение
    языка по полному имени (`Makefile`, `.gitignore`); в начале path — далеко от имени, к
    которому относится.

О12 (Р7). Строчная буква диска (`C:` → `/c:`) — прежнее правило: сливала `C:/x` и `c:/x`.

О13 (Р7, раздел 4). Закрыть предел различимости: NFC/NFD пришлось бы помечать в каждой букве с
    диакритикой из архивов с macOS, которые пишут имена в NFD; гомоглифы — экранировать всё
    не-ASCII; ZWJ, ZWNJ и селекторы вариантов — экранировать, ломая эмодзи и письменности. Это
    испортило бы обычные имена ради случаев, к которым люди и так привыкли.

О14 (Р8). Не учитывать fragment при проверке каноничности. Генератор fragment не создаёт, но его
    может добавить чужой код (ссылка вида `#L10`), и `openTextDocument` открыл бы второй
    документ той же записи.

О15 (Р11). Конкретная ошибка в контракте (`FileNotFound`) — прежняя редакция: часть контракта
    провайдера, на которую никто не опирается и которая устаревала бы вместе с API VS Code.


# Приложение. Что APPNOTE говорит об именах

https://pkwaredownloads.blob.core.windows.net/pkware-general/Documentation/APPNOTE-6.3.9.TXT

Запрещено (4.4.17.1):
- буква диска или устройства (`C:/a.txt`);
- ведущий слэш (`/etc/passwd`);
- разделитель пути — только `/`.
При бите 11 имя в UTF-8, без него — CP437, где допустим любой байт.

Не запрещено: дубликаты, сегменты `..`, `.` и пустые, файл `a` рядом с `a/`, пустое имя (ввод
со стандартного входа), NUL и управляющие символы.

Запрещённое всё равно встречается в архивах, поэтому формат адресует и такие имена (Т1):
отказаться открывать архив — решение читателя архива, не формата URI.
