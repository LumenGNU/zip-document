# Слепая реализация

Проверка утверждения docs/URI.txt: «по разделам 2–3 две независимые реализации обязаны получить
один и тот же URI и одинаково решить, принимать ли чужой». Несколько моделей (или людей)
реализуют формат по одному только тексту контракта, прогон сравнивает каждую реализацию с
`../uri.js`.

1. `node make-prompt.js` — собрать `PROMPT.md`: задание (`task.md`) и разделы 1–3 спецификации,
   без разделов 4–8 и без ссылки на `uri.js`. Пересобирать после каждой правки docs/URI.txt.
2. Отдать `PROMPT.md` модели целиком, в новом разговоре, без других файлов проекта.
3. Ответ сохранить как `impls/<модель>.js`.
4. `node run.js impls/<модель>.js [impls/<другая>.js ...]` (из этого каталога; `vscode-uri`
   берётся из `../node_modules`). Параметры: `SEED` (1), `N` — число случайных троек (3000),
   `SHOW` — примеров на категорию (3).

Что сравнивается. Случайные тройки (архив, байты имени, index) из трудных кусков: `/`, `.`, `..`,
`C:`, `%`, `&`, `#`, управляющие и невидимые символы, символы направления, ZWJ и селекторы,
`⟦`, `⟧`, байты вне UTF-8. Для каждой — `build`; `parse` канонического URI (объектом и после
строки); `parse` 40 видов испорченного URI (authority, fragment, path, порядок и значения
параметров, формы E, N и P) и четырёх случайных правок. Ожидаемый ответ всегда берётся у
`../uri.js`, а не предполагается.

Как читать расхождение. Это не приговор реализации: это место, где два прочтения раздела 3
разошлись. Ошибка модели — исправлять ничего не нужно; неоднозначность текста — править раздел 3
(и пересобрать `PROMPT.md`); ошибка `uri.js` — править его (он не определяет контракт). Список
НЕОДНОЗНАЧНОСТИ в начале каждого ответа читать даже при нуле расхождений.

Самопроверка: `impls/_reference.js` — `../uri.js` за интерфейсом задания, расхождений 0. Семь
нарочно испорченных копий `uri.js` (fragment не проверяется, `⟦` не экранируется, NFC, сегменты
`.`/`..` не помечаются, строчная буква диска, `index=0` пишется, ZWJ экранируется) прогон ловит
все (2026-11-08).

## Бенчмарк

`node bench.js [impls/<имя>.js ...]` (по умолчанию — все файлы `impls`); `SEED` (1), `N` —
испорченных URI на зерно (6000). Не рейтинг: соответствие — да или нет, остальное — таблица
свойств, которые на результат не влияют. Итогового балла нет — веса пришлось бы выдумать.

- Консенсус. Канонические URI трудных имён (`a/`, пустое, `C:x`, `..`, `⟦`, `d\a/b`; index 0, 1,
  12), испорченные 1–3 случайными правками path, query, authority, fragment; каждый отдаётся
  `parse` всех реализаций. Ожидаемого ответа нет, `uri.js` голосует наравне с остальными
  (`_reference`); любое меньшинство — расхождение, разбирать как в `run.js`. Код выхода 1 при
  расхождении.
- Таблица: строки кода без комментариев; мс на имя в 64 КиБ — видно квадратичную работу, если
  она есть; сколько раз реализация была в меньшинстве; поведение вне контракта задания (`build` без index, срез `Buffer` со смещением,
  отказ на дробный, отрицательный, 2^53 index; `parse` от `null`, строки, `{}`, объекта с
  бросающим геттером; общая память у двух результатов `parse`).

Самопроверка: `uri.js` без проверки fragment в компании `opus-6`, `sonnet-6`, `fable-6` консенсус
ставит в меньшинство — 319 из 5025 URI (N 2000), код выхода 1 (2026-11-09).

Первый прогон (2026-11-09, 31 реализация и `_reference`, около 18 с): 15 044 URI, все приняли
одни и те же 1079, расхождений 0. Имя в 64 КиБ — 6–53 мс, квадратичного роста нет ни у кого. Вне контракта: `uri.js` бросает исключение на `parse(null)` и на бросающий

Списки насыщаются: большая часть пунктов — пересказ выбранного прочтения, совпадающего с
текстом, а не вопрос к нему.

Пункт про P оказался находкой, но не в тексте, а в `uri.js`. Проверка утверждения «у URI архива
условия на P выполняются всегда» его опровергла: toString() вставляет порт (часть authority
после последнего `:`) как есть, и при порте вроде `h:1&2` или `h:%41` P не каноничен. `uri.js`
для такого архива строил URI, который сам же отвергал. Теперь генератор отказывает, а 3.3
говорит прямо: URI записи есть, только если P удовлетворяет условиям, иначе генератор
отказывает (3.3, Р4, 6.1; проверки в `check.js`).

`run.js` этого не видел: все его архивы с обычными портами. Добавлены две категории — архивы с
портами `1&2`, `1=2`, `%41`, `1#2`: `build` обязан отказать (любым исключением), а `parse` URI,
который построил бы генератор без проверки, — вернуть null. Порт `x/y` в список не вошёл: строка
`http://h:x/y/x.zip` после Uri.parse — другой объект (authority `h:x`), но та же строка, P
каноничен, и URI у записи есть. Все реализации, перепрогнанные с новыми категориями (зерно 1):
- `_reference.js` и 10 реализаций — 0 расхождений: P проверяют в `build`, URI с негодным P не
  принимают;
- `sonnet.js` (первый прогон) — `build` не отказывает ни на одном из четырёх (в его списке так и
  записано: «брать toString() как есть и не проверять»);
- `haiku.js` и `haiku-2.js` — `build` не отказывает на двух портах из четырёх, а URI с "=" в P
  `parse` принимает.
Все три — по тексту до этой правки, где условия на P стояли как утверждение, а не как условие.

## Сводка по шести прогонам

  и сравнивается по пяти полям. Отдельных проверок path регулярными выражениями нет ни у кого.
- Метку обратно не разбирает никто: обратимость метки для совместимости не понадобилась (после
  этого наблюдения она перенесена из 3.5 в раздел 4 как следствие).
- `build` — `URI.from` по компонентам; склейки строки и `joinPath` нет.
- E — base64url через `Buffer`, каноничность — сравнением с перекодированием.
- Шаг 1 — свой побайтовый цикл; `TextDecoder` нет ни у кого.
- Таблица шага 2 — массив диапазонов; `\p{…}` из среды нет ни у кого — заморозка списка
  выдержана.
- `URI.parse(P)` — нестрогий у всех 24 (строгий только у `uri.js`); режим поэтому и оставлен
  незаданным (3.3).
- `parse` принимает любой объект с нужными полями; `null`, строка, `{}` → `null`.

Различия — только в записи, не в результате:

Вне контракта задания:
