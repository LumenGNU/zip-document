# Слепая реализация

Проверка утверждения docs/URI.txt: «по разделам 2–3 две независимые реализации обязаны получить
один и тот же URI и одинаково решить, принимать ли чужой». Несколько моделей (или людей)
реализуют формат по одному только тексту контракта, прогон сравнивает каждую реализацию с
`../uri.js`.

1. `node make-prompt.js` — собрать `PROMPT.md`: задание (`task.md`) и разделы 1–3 спецификации,
   без разделов 4–8 и без ссылки на `uri.js`. Пересобирать после каждой правки docs/URI.txt.
2. Отдать `PROMPT.md` модели целиком, в новом разговоре, без других файлов проекта.
3. Ответ сохранить как `impls/<модель>.js`.
4. `node run.js impls/<модель>.js [impls/<другая>.js ...]` (из этого каталога; `vscode-uri`
   берётся из `../node_modules`). Параметры: `SEED` (1), `N` — число случайных троек (3000),
   `SHOW` — примеров на категорию (3).

Что сравнивается. Случайные тройки (архив, байты имени, index) из трудных кусков: `/`, `.`, `..`,
`C:`, `%`, `&`, `#`, управляющие и невидимые символы, символы направления, ZWJ и селекторы,
`⟦`, `⟧`, байты вне UTF-8. Для каждой — `build`; `parse` канонического URI (объектом и после
строки); `parse` 40 видов испорченного URI (authority, fragment, path, порядок и значения
параметров, формы E, N и P) и четырёх случайных правок. Ожидаемый ответ всегда берётся у
`../uri.js`, а не предполагается.

Как читать расхождение. Это не приговор реализации: это место, где два прочтения раздела 3
разошлись. Ошибка модели — исправлять ничего не нужно; неоднозначность текста — править раздел 3
(и пересобрать `PROMPT.md`); ошибка `uri.js` — править его (он не определяет контракт). Список
НЕОДНОЗНАЧНОСТИ в начале каждого ответа читать даже при нуле расхождений.

Самопроверка: `impls/_reference.js` — `../uri.js` за интерфейсом задания, расхождений 0. Семь
нарочно испорченных копий `uri.js` (fragment не проверяется, `⟦` не экранируется, NFC, сегменты
`.`/`..` не помечаются, строчная буква диска, `index=0` пишется, ZWJ экранируется) прогон ловит
все (2026-11-08).

## Прогон 2026-11-09

`PROMPT.md` после переименования `pkg` → `archive` и уточнения шага 8 (`⟦U+XXXX⟧` с примером
`/C:` вместо `⟦U+00XX⟧`, где X путался с буквой диска). Четыре модели, каждая в отдельном
разговоре, видели только `PROMPT.md` и `vscode-uri`: `impls/opus.js` (Opus 5.5),
`impls/sonnet.js` (Sonnet 5.5), `impls/haiku.js` (Haiku 5.5), `impls/fable.js` (Fable 5.1).

Результат: 0 расхождений у всех четырёх на зёрнах 1 (N 3000), 2 и 3 (N 5000) — 140–235 тысяч
сравнений на прогон.

Наблюдения о реализациях:
- Все четыре проверяют каноничность одинаково и так, как `uri.js` (раздел 7): извлечь тройку из
  query, построить URI заново, сравнить пять компонентов. Отдельных регулярных выражений для
  path никто не писал — определение 3.4 подталкивает к этому само.
- E везде принимается только если совпадает с перекодированием своих байтов; к этому пришли из
  примеров 3.4 ("QR", "QQ==", "+/8"), хотя двое назвали строгость E заданной лишь примерами.
- Шаг 1 — у всех свой побайтовый цикл, TextDecoder не использован; оборванная
  последовательность — по одному "⟦HH⟧" на байт.
- P у всех разбирается нестрогим `URI.parse(P)` (у `uri.js` строгий). На результат не влияет:
  строку без схемы отсекает сравнение `toString()`.
- Шаг 8 после правки никто неоднозначным не назвал, все реализовали верно.
- Объём: 122–215 строк.

НЕОДНОЗНАЧНОСТИ, общие для нескольких моделей, и что с ними сделано:
- Что делает `build`, когда URI нет (index > 2^53 − 1, негодный P) — все четыре; все бросают
  исключение. В 3.4 дописано: генератор отказывает.
- Пустой последний сегмент у записи каталога (имя `/`): применяется ли шаг 5 к `⟦⟧` — две
  модели; обе прочли верно, по порядку шагов. В 3.7 добавлен пример `/` → `/⟦⟧⟦U+002F⟧`.
- Сколько байтов экранировать в оборванной последовательности UTF-8 — три; текст («чтение
  продолжается со следующего байта») уже однозначен, все прочли одинаково. Не правилось.
- Остальное (проверка типов входа `parse`, строгость `URI.parse`, способ проверки
  каноничности) — на результат не влияет или прямо следует из 3.4. Не правилось.
