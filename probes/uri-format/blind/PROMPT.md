# Задание: независимая реализация формата URI записи ZIP-архива

Ниже — нормативная часть спецификации формата (разделы 1–3). Реализуй по ней формат на
JavaScript. Ту же задачу независимо решают другие; реализации будут сравниваться между собой на
большом числе входов. Цель — проверить, что текст спецификации однозначен, поэтому важна не
красота кода, а точное следование тексту.

Правила:
- Опирайся только на приложенный текст. Ссылки вида [Р3], [О2] и на разделы 4–8 ведут в
  ненормативные части (обоснования, проверка, заметки по реализации), они намеренно не
  приложены. Если без них правило не понять — это тоже находка (см. ниже).
- Не задавай вопросов. Где текст допускает больше одного прочтения, выбери одно, реализуй его
  и запиши в список НЕОДНОЗНАЧНОСТИ.
- Node.js 22, CommonJS, один файл, без ввода-вывода. Единственная зависимость — пакет
  `vscode-uri` версии 3.0.8: `const { URI } = require('vscode-uri')`. Его класс `URI` — то, что
  в тексте называется `vscode.Uri`: поля `scheme`, `authority`, `path`, `query`, `fragment`;
  `URI.from`, `URI.parse`, `toString()`. Это та же реализация URI, что в самом VS Code.

Интерфейс:

```js
module.exports = {
  // archive — URI архива (объект URI); name — байты имени записи (Uint8Array);
  // index — целое число >= 0. Возвращает канонический URI записи (объект URI).
  build(archive, name, index) { /* ... */ },

  // uri — URI, который получил провайдер (объект URI, любой схемы и вида).
  // Канонический URI записи -> { archive: URI, name: Uint8Array, index: number };
  // любой другой -> null. Исключений не бросает.
  parse(uri) { /* ... */ },
};
```

Ответ — один файл целиком. В его начале — комментарий:

```js

// - <раздел или шаг>: <что неясно>; выбрано: <что реализовано>
// (или одна строка «нет»)
```

Тесты не пиши: их прогонит проверяющий.

# 1. Назначение

URI нужен, чтобы VS Code открывал запись ZIP-архива как файл: вкладка, языковой режим, иконка,
`watch`, `workspace.fs`. Строит его редактор архива (переход по записи), разбирает провайдер
файловой системы схемы `zip-document`; остальные — VS Code, другие расширения — передают его как
есть.

Не решает: иерархию каталогов — `readDirectory`, архив как папка рабочей области [Р12];
относительные ссылки между записями [Р7]; отождествление одного архива под разными URI [Р4].

Цели формата (Т1–Т8). Они определяют, какие свойства должен обеспечить контракт; сами правила
заданы в разделе 3, как цели достигнуты и где их пределы — в разделе 4.

Т1. Достижимость: у каждой записи центрального каталога есть URI — при любом имени, в том числе
    пустом, с `..`, ведущим `/`, недекодируемыми байтами, и при дубликатах имён.
Т2. Единственность: у записи ровно один URI, и из URI, дошедших до провайдера, он принимает
    только его. Для VS Code у записи поэтому один ресурс: один TextDocument, одна вкладка, один
    `watch`.
Т3. Устойчивость к VS Code: URI доходит до провайдера без изменений любым путём — `workspace.fs`,
    `openTextDocument`, `vscode.open`, и через строку `toString()` → `Uri.parse`.
Т4. Стабильность: URI не зависит от данных записи, её метаданных и других записей, кроме
    одноимённых. После пересборки архива и изменения данных URI тот же, если сохранились имя и
    порядок среди одноимённых; той же записью между версиями архива считается именно это (раздел 2).
Т5. Вложенность: архивом может быть запись другого архива.
Т6. Проверка без чтения архива: каноничен ли URI, решается по одному URI.
Т7. Удобство: заголовок вкладки, языковой режим и иконка — по имени записи; имя читается как
    есть, без процентного кодирования.
Т8. Различимость. Строго: у разных записей одного архива разный path, и VS Code различает их
    вкладки. На глаз: явно показаны строение имени (сегменты `""`, `.`, `..`, завершающий `/`),
    номер дубликата, байты вне UTF-8, управляющие, невидимые и пробельные символы — кроме тех,
    без которых текст отображается неправильно (ZWJ, ZWNJ, селекторы вариантов, 3.2). Что на глаз
    не различить и почему это принято — раздел 4.

Термины:
- запись — запись центрального каталога архива;
- имя — байты поля имени записи в центральном каталоге (не Unicode Path Extra Field 0x7075, не
  имя из локального заголовка) [Р2];
- одноимённые записи, дубликаты — записи с побайтно равными именами;
- index — номер записи среди одноимённых в порядке центрального каталога, с 0 [Р3];
- запись каталога — запись, имя которой оканчивается на `/`;
- архив — ресурс VS Code с ZIP-архивом, задан своим URI любой схемы, в том числе `zip-document`;
- метка — path URI записи;
- генератор — код, который строит URI записи; провайдер — `FileSystemProvider` схемы
  `zip-document`.


# 2. Модель адресации

Запись задаётся тройкой (URI архива, имя, index). Больше формат о записи ничего не знает: данные,
даты, флаги, extra-поля, смещения, соседние записи в адрес не входят.

index — позиция среди одноимённых записей, а не идентичность содержимого. Если в пересобранном
архиве одноимённые записи переставлены, их URI остаются прежними, а под ними — другие данные.
Одноимённые записи ничем, кроме порядка, не различаются, и формат не пытается узнавать их между
версиями архива [Р3].

Компоненты URI делят обязанности:
- query — адрес: URI архива, имя, index [Р1];
- path — метка: однозначно получается из (имя, index) и обратно; показывает запись человеку и
  VS Code, но адресом не служит [Р1, Р7];
- authority — версия формата [Р9];
- scheme — владелец формата [Р10];
- fragment — не используется [Р8].

У каждой тройки ровно один URI — канонический (3.4). Любой другой URI схемы `zip-document` — не
URI записи.


# 3. Контракт

## 3.1 Компоненты

Компоненты — поля `vscode.Uri`.

scheme     `zip-document`. [Р10]
authority  `v1`. [Р9]
path       метка, 3.2. [Р1, Р7]
query      адрес, 3.3. [Р1, Р3–Р6]
fragment   пустой. [Р8]


## 3.2 Метка (path)

Экранирование — `⟦…⟧` (U+27E6, U+27E7). Формы:
  `⟦HH⟧`              байт, не входящий в корректную последовательность UTF-8; HH — две заглавные
                      шестнадцатеричные цифры;
  `⟦U+XXXX⟧`          символ, который не показывается как есть; XXXX — заглавные
                      шестнадцатеричные цифры, не меньше четырёх, без лишних ведущих нулей;
  `⟦⟧` `⟦.⟧` `⟦..⟧`   сегмент, равный строго `""`, `.`, `..`;
  `⟦#N⟧`              номер дубликата, N = index ≥ 1, десятичное без ведущих нулей.

Метка из (имя, index):
1. Байты имени читаются слева направо. Корректная последовательность UTF-8 (RFC 3629: без
   избыточных форм, без суррогатов, не выше U+10FFFF) — её символ; любой другой байт — `⟦HH⟧`,
   и чтение продолжается со следующего байта.
2. Символ из списка ниже — `⟦U+XXXX⟧`, остальные — как есть.
3. Один завершающий `/` (признак записи каталога) снимается и запоминается.
4. Строка делится по `/`. Сегмент, равный строго `""`, `.`, `..`, заменяется на `⟦⟧`, `⟦.⟧`,
   `⟦..⟧`. Ни один сегмент не отбрасывается и не разрешается.
5. Если был снят завершающий `/` — к последнему сегменту дописывается `⟦U+002F⟧`.
6. index ≥ 1 — перед последним сегментом вставляется сегмент `⟦#index⟧`.
7. path = `/` + сегменты через `/`.
8. path начинается с `/X:`, где X — заглавная латинская буква A–Z, — X заменяется на
   `⟦U+00XX⟧`.

Список символов шага 2 — замороженный. Нормативна таблица ниже; получена она так: по Unicode 17.0
объединение категорий Cc, Cf, Zl, Zp, Zs и свойств Default_Ignorable_Code_Point,
Noncharacter_Code_Point, из него исключены U+0020, ZWJ U+200D, ZWNJ U+200C и селекторы
вариантов (FE00–FE0F, E0100–E01EF, монгольские 180B–180D и 180F), добавлен сам `⟦` U+27E6:
  0000–001F  007F–00A0  00AD  034F  0600–0605  061C  06DD  070F  0890–0891  08E2
  115F–1160  1680  17B4–17B5  180E  2000–200B  200E–200F  2028–202F  205F–206F
  27E6  3000  3164  FDD0–FDEF  FEFF  FFA0  FFF0–FFFB  FFFE–FFFF  110BD  110CD
  13430–1343F  1BCA0–1BCA3  1D173–1D17A  E0000–E00FF  E01F0–E0FFF
  и nFFFE–nFFFF в плоскостях 1–16.
Исключённые символы остаются как есть (Р7). Никакой другой обработки нет, в том числе
нормализации Unicode: регистр, NFC/NFD, пробел U+0020, `\`, `%`, `?`, `#`, `⟧` остаются как есть.

Свойства метки — следуют из шагов, на них опираются гарантии раздела 4:
- начинается с `/`; нет сегментов `""`, `.`, `..`; не оканчивается на `/`; не начинается с
  `/X:` (X — A–Z);
- вне экранирований нет ни одного символа списка шага 2;
- по метке однозначно восстанавливаются имя и index (3.5).


## 3.3 Адрес (query)

query — ровно эта строка, параметры в этом порядке, разделитель `&`:

  pkg=<P>&entry=<E>            для index = 0
  pkg=<P>&entry=<E>&index=<N>  для index ≥ 1

P — `toString()` URI архива [Р4]. P не содержит `&` и `=` (их кодирует `toString()`) и
    совпадает со своим `toString(Uri.parse(P))`.
E — имя, base64url (RFC 4648 §5) без паддинга. Пустое имя — пустая строка (`entry=`). [Р2, Р6]
N — index, десятичное без ведущих нулей, от 1 до 2^53 − 1; при index = 0 параметр не пишется.
    Для index больше 2^53 − 1 URI нет. [Р3]


## 3.4 Каноническая форма; генератор и провайдер

URI каноничен, если он покомпонентно — scheme, authority, path, query, fragment, строгим
равенством строк — равен URI, построенному по 3.1–3.3 из какой-либо тройки (архив, имя, index).
Тройка, если она есть, извлекается из query однозначно: query делится по `&` на 2 или 3 части с
префиксами `pkg=`, `entry=`, `index=` по порядку; значения берутся как есть, без процентного
декодирования и без правил форм (`+` — не пробел) [Р5].

Каноничность — свойство URI, который получил провайдер. Что VS Code делает с URI до провайдера
(приводит authority к нижнему регистру, отбрасывает fragment, нормализует path), контракт не
определяет и провайдер увидеть не может; что из этого следует — раздел 4, Т2.

Генератор строит только канонические URI.

Провайдер:
- неканонический URI не обслуживает: на любой вызов (`stat`, `readFile`, `watch`, …)
  отвечает отказом и записи не читает; каким именно отказом — не часть формата [Р11];
- не исправляет URI на канонический [Р11];
- по каноническому URI читает запись архива P с этим именем и этим index;
- регистрирует схему как чувствительную к регистру (`isCaseSensitive: true`), как и
  определение каноничности: иначе VS Code мог бы свести к одному ресурсу канонический URI и
  неканонический, path которых различается только регистром, и провайдер получил бы не тот.

Из определения следует, что не каноничны, например:
- authority `V1`, `v2`, пустая; непустой fragment;
- path, не равный метке: `/B` при `entry=QQ` (имя `A`), `/./A`, метка по другой версии правил;
- параметры в другом порядке, лишние, повторённые, без `entry`;
- E не в канонической форме: `QR`, `QQ==`, `Q Q`, `QQ!` (все они при нестрогом декодировании
  дают байт `A`), `+/8` (base64, не base64url);
- `index=0`, `index=`, `index=01`, `index=1e1`, `index=-1`, больше 2^53 − 1;
- P, не равный своему `toString()`: `file:///C:/x.zip` вместо `file:///c%3A/x.zip`; пустой.


## 3.5 Обратимость

По каноническому URI восстанавливается тройка: архив — `Uri.parse(P)`, имя — декодирование E,
index — N или 0.

По метке, без query, восстанавливаются имя и index: символ вне экранирования — его байты UTF-8;
`⟦HH⟧` — байт; `⟦U+XXXX⟧` — байты UTF-8 символа; `⟦⟧`, `⟦.⟧`, `⟦..⟧` — сегмент `""`, `.`,
`..`; `⟦U+002F⟧` в конце — завершающий `/`; сегмент `⟦#N⟧` — index, сам он в имя не входит;
`/` вне экранирований — разделитель. Однозначно, потому что каждый `⟦` в метке открывает
экранирование: настоящий `⟦` из имени экранирован.


## 3.6 Строковая форма

Строка URI — `uri.toString()`, обратно — `Uri.parse(s)`. `toString()` процентно кодирует в
компонентах всё, кроме `A–Z a–z 0–9 - . _ ~` (и `/` в path): разделители формата в query
становятся `%3D` и `%26`, `%` из P — `%25`, символы метки вне ASCII — UTF-8 в `%XX`; E
остаётся как есть. Это кодирование VS Code, не формата: на уровне полей `Uri`
компоненты такие, как в 3.1–3.3.
