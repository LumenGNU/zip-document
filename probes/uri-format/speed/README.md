# Скорость построения URI записи

Провайдер строит URI для каждой записи архива; в большом архиве это заметно. Здесь — замер
скорости и быстрый вариант `../uri.js`.

- `perf.js` — замер; `node perf.js [<реализация>.js ...]`, по умолчанию `fast.js` и
  `../blind/impls/_reference.js` (`../uri.js` за тем же интерфейсом); слепые —
  `node perf.js ../blind/impls/*.js`. `ENTRIES` (100000), `RUNS` (7).
- `fast.js` — тот же формат, быстрее; интерфейс — как у слепых реализаций (`../blind/PROMPT.md`),
  поэтому проверяется их же прогонами, из `../blind`: `node run.js ../speed/fast.js` (зёрна 1–3)
  и `node bench.js impls/*.js ../speed/fast.js` (консенсус). На 2026-11-09 — 0 расхождений.

## Как меряется

Каждая реализация — в своём процессе: в одном процессе они делят JIT-состояние vscode-uri, и числа
плавают в 5 раз. Архив из 100 000 имён вроде дерева исходников и node_modules (в среднем 35 байт,
10% каталогов, немного не-ASCII, редкие экранируемые символы и битый UTF-8), каждая 50-я запись с
index 1. `build` всех записей, затем `parse` всех построенных URI; URI не выбрасываются, так что
сборка мусора входит в цену. Медиана из 7 проходов, разброс между проходами — до ×1,6.

## Прогон 2026-11-09

Мкс на запись:

| | build | parse |
|---|---|---|
| `fast.js` | 1,8 | 2,4 |
| лучшие слепые (`deepseek`, `sonnet-3`, `fable-3`) | 5,4–7,4 | 5,7–8,9 |
| большинство слепых | 8–11 | 10–14 |
| `uri.js` | 9,9 | 14,2 |
| `opus-2`, `opus-3`, `opus-5`, `fable-2` | 26–27 | 29–33 |

`sonnet` (5,4) быстр отчасти потому, что писался до правки 3.3 и не проверяет P в `build`.

Куда уходит время у `uri.js` (мкс на запись): метка (шаги 1–8) — 6,9; проверка P
(`toString(Uri.parse(P))`) — 1,1 на каждый вызов, хотя P у всех записей архива один; base64url
через `Buffer.from` с копией — 0,36; `URI.from` готовых частей — 0,27. Медленные четыре слепые
теряют на таблице шага 2: `for (const [a, b] of RANGES)` — деструктуризация на каждый символ на
каждый диапазон; цепочка `if` (`deepseek`) или `r[0]`, `r[1]` по индексу в разы быстрее.

## Что в `fast.js` иначе

- Таблица шага 2 — 64 КиБ `Uint8Array` для BMP, перебор только для 23 диапазонов вне BMP.
- UTF-8 проверяется одним проходом, чистые участки декодируются одним вызовом `utf8Slice`, без
  массива и `String.fromCodePoint` на символ; печатный ASCII не проверяется по таблице вовсе.
- Сегменты `""`, `.`, `..` ищутся по байтам (шаг 2 никогда не даёт `/` и `.` из других байтов),
  и без них шаги 3–8 — склейка строк без `split`/`map`/`join`.
- P проверяется один раз на объект архива (`WeakMap`), `parse` помнит последний P.
- `parse` сравнивает query и path с тем, какими они должны быть, а не строит URI.

Имя в 64 КиБ — 0,4 мс (у остальных 6–53). Нижняя граница при этом устройстве — около 0,76 мкс на
запись: `utf8Slice` (0,23–0,28) + `base64urlSlice` (0,2) + `URI.from` (0,28); остальное в 1,3 мкс
(без хранения URI) — проход по байтам и склейка.

## Дороже build

То, что делает с URI сам vscode-uri (тот же код, что в VS Code): `toString()` URI записи стоит
6–14 мкс, и после него на URI остаётся около 3,5–3,8 КБ (кэш `_formatted`; архив с путём в 45
символов; по-видимому, строка-верёвка от посимвольного кодирования query), против 56 байт у
`file:` URI; сам URI без `toString()` — около 280 байт. Миллион записей с вызванным `toString()`
— порядка 4 ГБ. Значит, URI записей строить и превращать в строку лениво — для видимых узлов
дерева и открытых записей, — а не на весь архив сразу, и не держать словари по `uri.toString()`
для всех записей.
